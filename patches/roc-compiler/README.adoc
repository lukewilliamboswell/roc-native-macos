= Compiler issues

Engine costs that turned out to be the Roc compiler's. The compiler is never
patched here: each issue has a reproducer and a write-up, to report to
roc-lang/roc. An engine patch that only works around one says so in its
header (xref:../roc-signals/README.adoc[patches/roc-signals]).

== The list

. `erased-captures/`: a call through an erased closure reads its captures
  borrowed, so a closure that updates the state it captures copies it on
  every call. Standalone reproducer. Engine impact: every turn copies the
  site storage on the event's path, which is linear in the sites of a block
  (see <<erased-captures>>). Upstream: not yet reported.
. `mount-sharing/`: in optimized builds the engine's mount passes its turn
  and its block shared, depending on the size of the functions involved,
  so appends copy. Reproduced with the engine only, not yet reduced.
  Worked around by engine patches 0001 and 0002 (see <<mount-sharing>>).
  Upstream: not yet reported.

Both reproduce with Roc 0.1.0 RC1 (`roc`) and nightly-2026-11-14-a87808d
(`roc-stable`), with `roc build` (LLVM, `--opt=speed`).

[#erased-captures]
== Erased closures borrow their captures

`erased-captures/main.roc` (basic-cli) is a state machine whose state is a
list its closure captures: `Step := [Step((U64 -> (Step, U64)))]`, each step
appends one item and returns the next machine. Appending to a uniquely held
list is amortized O(1), so the time per step should be constant. The program
also has a function returning `Box(Step)`. A `Box` is an erasure boundary by
its type alone (`src/postcheck/lambda_solved/solve.zig`: every function a box
holds is erased), so every `Step` closure is erased, and a call through an
erased closure gets its captures through a pointer into the closure's
allocation (`native_callable.drivePending`, `erased.capturePtr`). The callee
treats them as borrowed: the list is shared for the whole call, the append
copies it, and the run is quadratic.

[source,sh]
----
cd patches/roc-compiler/erased-captures
roc build main.roc --output=/tmp/erased && /tmp/erased
----

|===
| N steps | RC1, ns per step | nightly-2026-11-14, ns per step | without `boxed`, ns per step

| 5,000 | 446 | 416 | 2
| 10,000 | 806 | 808 | under 1
| 20,000 | 1,676 | 1,674 | under 1
| 40,000 | 3,299 | 3,288 | 1
|===

Deleting `boxed` (and its one use) makes it linear. `roc main.roc` (not an
optimized build) is linear with RC1.

Expected: when the call owns the closure (ARC's deferred-call transfer) and
its allocation is unique, the callee could take the captures over (move
them out and free the allocation) instead of borrowing them, so a closure
that threads its state through its captures updates it in place.

Engine impact. Every dynamic site of roc-signals is a closure (`Inst`)
that owns its typed storage, and the platform root boxes the engine's state
for the host, so all of them are erased. A turn calls the root instance and
each site on the event's path; each one rebuilds its block, and with the
captures borrowed each rebuilt list is a copy. In the grid bench at
N = 100 (10,000 `Engine.state` cells in one block), lldb shows a
2,400,000-byte `memcpy` (10,000 children of 240 bytes) from the
`List.replace` in `Core.fire_kid`, inside the root instance's erased call,
on every `Fire` of a hover turn, with an incref of every copied child and a
decref of every old one. That is most of the hover turn's 2.4 ms: the turn
is linear in the number of sites in the block on the event's path, against
roc-signals' rule that work is proportional to what changed. A simpler `Box`
handle in `platform/main.roc` did not change it (the state's type is boxed
either way).

[#mount-sharing]
== Mount shares its turn and its block

`mount-sharing/main.roc` is an app on this platform that mounts N static
boxes with seven attributes (`-v attrs`) or N `Engine.state` cells
(`-v sites`). With the pristine engine (reverse-apply engine patches 0002
and 0001), mounting is quadratic in optimized builds: in `mount_elem`'s
attribute loop the command buffer (`Tx.cmds`) has refcount 2 when an
attribute's command is appended, and in its `Site` branch the block's child
lists have refcount 2 when `add_child` appends (an lldb watchpoint on the
fresh copy's refcount shows an incref inside `mount_elem` just before the
append). `--opt=dev` builds and `--specialize=no` builds are linear.

The sharing depends on the size of the functions, not on what they do:
removing any one of `mount_attr`'s branches (the trivial `Property` one
included) made the attribute loop linear, and the site appends became
linear only once the `Element` and the text branches were both moved out of
`mount_elem`. Engine patches 0001 and 0002 move them into functions of
their own. Attempts to reduce this to a standalone program (the same loop
shapes, records, closures and branch counts without the engine) stayed
linear, so this is reported with the engine as the reproducer.

Engine time of the mount (ms, the `mount engine` figure the host prints
under `ROC_BENCH=1`, as in
`ROC_BENCH=1 ROC_SCRIPT='stats;quit' ./main -n 4900 -v sites`):

|===
| Variant, N | pristine | patches 0001 + 0002

| `attrs`, 1,024 | 44 | 6.5
| `attrs`, 2,500 | 221 | 14
| `attrs`, 4,900 | 1,792 | 26
| `sites`, 1,024 | 71 | 10
| `sites`, 2,500 | 381 | 21
| `sites`, 4,900 | 2,858 | 44
|===
