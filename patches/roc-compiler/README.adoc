= Compiler issues

Engine costs that turned out to be the Roc compiler's. The compiler is never
patched here: each issue has a reproducer and a write-up, to report to
roc-lang/roc. The engine patches named below (0001 to 0005) were this
repository's series on roc-signals, which carried the workarounds until
roc-signals 0.8.0-rc2 took them: 0001 to 0005 are roc-signals#305 to #309,
and the measurements below are the ones taken on that series.

== The list

. `erased-captures/`: a call through an erased closure reads its captures
  borrowed when the call is in tail position or the closure's result holds
  exactly one function, so a closure that rebuilds itself from the state it
  captures copies that state on every call. Standalone reproducer of the
  four combinations. Engine impact: every turn copied the child list of
  each block on the event's path; worked around by engine patch 0003 (see
  <<erased-captures>>). Upstream:
  https://github.com/roc-lang/roc/issues/13374[roc-lang/roc#13374].
. `mount-sharing/`: in optimized builds the engine's mount passes its turn
  and its block shared, depending on the size of the functions involved,
  so appends copy. Reproduced with the engine only, not yet reduced.
  Worked around by engine patches 0001 and 0002 (see <<mount-sharing>>).
  Upstream: not yet reported.
. `dict-update-sharing/`: a dictionary grown with `Dict.update` in a
  method of a nominal record, called in a `var` loop, is shared when it
  grows, so each update copies it. Standalone reproducer. Engine impact:
  building a table with `Table.insert` in a loop was quadratic; worked
  around by engine patch 0004 (see <<dict-update-sharing>>). Upstream:
  https://github.com/roc-lang/roc/issues/13377[roc-lang/roc#13377].
. `destructure-sharing/`: a record taken apart by a destructuring
  statement or a parameter pattern keeps its refcounted fields shared
  until the function returns, so an update of one of them copies it.
  Standalone reproducer. Engine impact: every table write copied the
  table's rows, and the root's pass read its block shared, so a
  `table_view` copied its columns on every turn; worked around by engine
  patches 0004 and 0005 (see <<destructure-sharing>>). Upstream:
  https://github.com/roc-lang/roc/issues/13376[roc-lang/roc#13376].

The first two reproduce with Roc 0.1.0 RC1 (`roc`) and nightly-2026-11-14-a87808d
(`roc-stable`), with `roc build` (LLVM, `--opt=speed`); `erased-captures`
also with nightly-2026-11-22-3350b1c.

[#erased-captures]
== Erased closures borrow their captures

Reported as https://github.com/roc-lang/roc/issues/13374[roc-lang/roc#13374]
(the text from "Title" to the end of "Suspected mechanism", with `main.roc`
as the program).

Title:: An erased closure that rebuilds itself copies its captures on every
call: a tail-position call never transfers it, and a single-function result
keeps it alive

Summary:: A closure that threads its state through its captures (each call
updates a captured list and returns the next closure) normally updates the
list in place. Once a value of its type is boxed, every function the type
holds is erased, and a call reads the closure's captures borrowed, so the
list is shared during the call and the update copies it: each call is
linear in the size of the state. This happens when the erased call is in
tail position, or when the closure's result holds exactly one function;
only a call that is neither is in place. Related to #13012 (closed), whose
shape (the closure returns a list, the caller builds the next closure) is
now in place.

Reproduction:: `erased-captures/main.roc` (basic-cli 0.28.1) runs the
machine `Step := [Step((U64 -> (Step, U64))), ...]` for N steps in four
combinations. `boxed_one` and `boxed_spare` name `Box(One)` and
`Box(Spare)`, on a path that never runs, which makes every function those
types hold erased. `tail_*` calls the closure in tail position, `bound_*`
binds the result and then returns it. `One` returns the next machine (the
result holds one function); `Spare` adds a variant `Spare(List(Spare))`,
never built, so the result also holds a list of functions. `Idle` and
`Spare` give `step` a recursive branch so it is not inlined.
+
[source,sh]
----
roc build main.roc --output=/tmp/erased && /tmp/erased
----

Expected:: Constant time per step in all four (each step appends one item
to a list it owns).

Actual:: Time per step grows linearly with N, so the run is quadratic,
except for `bound_spare`. Apple M-series, `roc build` (LLVM,
`--opt=speed`), ns per step:
+
|===
| N | tail_one | bound_one | tail_spare | bound_spare | all four without the `Box`

6+| Roc 0.1.0 RC1
| 5,000 | 621 | 604 | 731 | 90 | 1–4
| 10,000 | 1,291 | 1,202 | 1,181 | 32 | 1–4
| 20,000 | 2,420 | 2,424 | 2,475 | 31 | 1–2
| 40,000 | 5,074 | 5,134 | 5,205 | 31 | 0–2
6+| nightly-2026-11-22-3350b1c
| 5,000 | 647 | 622 | 632 | 32 | not run
| 10,000 | 1,200 | 1,703 | 1,271 | 31 | not run
| 20,000 | 2,584 | 2,698 | 2,790 | 34 | not run
| 40,000 | 5,202 | 5,381 | 5,298 | 35 | not run
|===
+
nightly-2026-11-14-a87808d is quadratic in all four, `bound_spare`
included (945 to 5,459 ns per step).

Suspected mechanism (compiler at 3ff191391f):: Both cases leave the callee
reading its capture record borrowed from a closure allocation that stays
alive for the whole call.
+
* Tail position. An erased call in tail position is deferred: it is
  recorded in the caller's pending cell and driven by
  `native_callable.drivePending` (`src/builtins/native_callable.zig`),
  which passes the closure as the reuse (ownership) argument only when the
  record's `transfer` is set. design.md ("A deferred `.lss` call keeps a
  retained closure reference for whoever drives it and never transfers")
  makes that never for `.lss`, so the driver keeps its reference, decrefs
  the closure after the call, and the callee's captures are shared.
* One function in the result. When the callee's result type holds exactly
  one erased-callable slot (`erasedResultDemand(entry.ret) ==
  .single_slot`, `src/postcheck/solved_lir_lower.zig`, where
  `current_erased_reuse` is set), the reuse argument is kept as the
  destination for that slot. design.md ("Constraints Per Statement Form",
  `erased_capture_load`): "emission selects `erased_capture_load_borrowed`
  while the owner stays live (a repack of the allocation as the
  procedure's result)". The owner stays live until the result is packed, so
  the captures are borrowed for the whole body, and only a result with no
  slot or an ambiguous one (a list of functions, or two) releases the
  allocation at entry and hands its captures over. Packing a closure of a
  different capture layout does not help (tried), since the destination
  is still threaded through.
+
What would fix both: a call that owns the closure, deferred or not, could
transfer it; and a callee that owns a unique closure could move its
captures out at entry (no incref) and keep the emptied allocation only as
the destination for its result, repacking into it as now.

Engine impact. Every dynamic site of roc-signals is a closure (`Inst`)
that owns its typed storage, and the platform root boxes the engine's
state for the host, so all of them are erased. `Core.call` called a site
in tail position, and a site's answer `(Inst(ctx), Out(ctx), Tx)` holds
exactly one function, so every site on the event's path read its block
shared, and rebuilding the block (`fire_kid`'s `List.replace`) copied its
child list. In the grid bench at N = 100 (10,000 `Engine.state` cells in
one block) that was a 2,400,000-byte `memcpy` (10,000 children of 240
bytes) per call, with an incref of every copied child and a decref of
every old one: most of a 2.5 ms hover turn, which was linear in the sites
of the blocks on the event's path. Engine patch 0003 avoids both cases (a
bound result in `call`, and a never-built `Spare(List(Inst(ctx)))`
variant), and the hover turn is about 0.1 ms at every size measured, up
to 14,400 cells. The grid's `--smoke` guards it.

[#mount-sharing]
== Mount shares its turn and its block

`mount-sharing/main.roc` is an app on this platform that mounts N static
boxes with seven attributes (`-v attrs`) or N `Engine.state` cells
(`-v sites`). With the pristine engine (reverse-apply engine patches 0002
and 0001), mounting is quadratic in optimized builds: in `mount_elem`'s
attribute loop the command buffer (`Tx.cmds`) has refcount 2 when an
attribute's command is appended, and in its `Site` branch the block's child
lists have refcount 2 when `add_child` appends (an lldb watchpoint on the
fresh copy's refcount shows an incref inside `mount_elem` just before the
append). `--opt=dev` builds and `--specialize=no` builds are linear.

The sharing depends on the size of the functions, not on what they do:
removing any one of `mount_attr`'s branches (the trivial `Property` one
included) made the attribute loop linear, and the site appends became
linear only once the `Element` and the text branches were both moved out of
`mount_elem`. Engine patches 0001 and 0002 move them into functions of
their own. Attempts to reduce this to a standalone program (the same loop
shapes, records, closures and branch counts without the engine) stayed
linear, so this is reported with the engine as the reproducer.

Engine time of the mount (ms, the `mount engine` figure the host prints
under `ROC_BENCH=1`, as in
`ROC_BENCH=1 ROC_SCRIPT='stats;quit' ./main -n 4900 -v sites`):

|===
| Variant, N | pristine | patches 0001 + 0002

| `attrs`, 1,024 | 44 | 6.5
| `attrs`, 2,500 | 221 | 14
| `attrs`, 4,900 | 1,792 | 26
| `sites`, 1,024 | 71 | 10
| `sites`, 2,500 | 381 | 21
| `sites`, 4,900 | 2,858 | 44
|===

[#destructure-sharing]
== Destructuring leaves the parts shared

Reported as https://github.com/roc-lang/roc/issues/13376[roc-lang/roc#13376] (the text from "Title" to the end
of "Notes", with `destructure-sharing/main.roc` as the program). It may be
what the engine's `TODO https://github.com/roc-lang/roc/issues/12957`
in `store_inst` describes ("an optimized build still copies a table's
rows on each keyed write").

Title:: Taking a record apart with a destructuring statement or a
parameter pattern keeps its fields shared, so updating one copies it

Summary:: `{ rows, other, version } = t` followed by `rows.insert(..)`
should insert in place when `t` is uniquely held. In an optimized build
it copies `rows` on every call when the record has a second refcounted
field and the function is called from a loop that is a procedure of its
own: the fields stay shared until the function returns. The same
function written with `match t { { rows, other, version } => .. }` is in
place. A parameter pattern (`|{ rows, other, version }, key, row|`)
behaves as the statement does. In the engine, a tuple taken apart by a
statement (`(a, b, c) = f(..)`) kept its parts shared the same way (not
reduced).

Reproduction:: `destructure-sharing/main.roc` (basic-cli 0.28.1) calls
three versions of the same write three times per loop, twenty loops, on
a record holding a `Dict(U64, { name : Str, value : U64 })` of N entries,
a `Str` and a counter:
+
[source,sh]
----
roc build main.roc --output=/tmp/destructure && /tmp/destructure
----

Expected:: Constant time per call in all three versions.

Actual:: The statement and the parameter pattern are linear in N; the
`match` is constant. Apple M-series, `roc build` (LLVM, `--opt=speed`),
microseconds per call of the loop (three inserts):
+
|===
| N | statement | parameter pattern | `match`

4+| Roc 0.1.0 RC1
| 10,000 | 80 | 82 | 0
| 100,000 | 1,274 | 1,290 | 0
| 1,000,000 | 17,339 | 17,291 | 0
4+| nightly-2026-11-22-3350b1c
| 10,000 | 85 | 85 | 0
| 100,000 | 1,534 | 1,475 | 0
| 1,000,000 | 18,112 | 17,445 | 0
|===

Notes:: Each of these makes the statement constant again: a record with
one refcounted field, dictionary values that are not refcounted (`U64`
instead of the record holding a `Str`), the three inserts written out
instead of in a loop, or the loop inlined into its only caller. In the
engine, a --debug build showed the copy as a `memcpy` of the
dictionary's entries in `Dict.insert`, and a watchpoint on their
refcount an incref before the insert that was released only after the
function returned.

Engine impact. Three places in the engine took a table, or the root
instance that owns every table view, apart this way, and each cost a
turn the size of a table (bench/rows, a turn writing 3 rows of a table
of a million: 63 to 80 ms):

* `TableCore.write`'s statement left the rows shared for the insert:
  each `Table.update` in an app's loop copied the rows.
* `Engine.inner`'s parameter pattern, inlined into the table cell's
  lens, and the lens handing its modifier a table it still held: the
  first write of each turn copied the rows.
* `turn`'s `(root2, out, tx2) = call(..)`: the root's pass for the
  written cells read the root block shared, replacing a child in its
  child list copied the list, and the table view below it copied its
  pending marks, a hole column and its shown column (196 MB at a million
  rows) on every turn.

Engine patch 0004 fixes the first two with `match` (and by keeping the
lens's table unwrapped until the call), and 0005 the third. A turn that
writes 3 rows now costs 0.1 to 0.3 ms at every size measured, up to a
million rows; bench/rows' `--smoke` guards it.

[#dict-update-sharing]
== Dict.update copies a dictionary the loop owns

Reported as https://github.com/roc-lang/roc/issues/13377[roc-lang/roc#13377] (from "Title" to the end of "Suspected
mechanism", with `dict-update-sharing/main.roc` as the program):

Title:: `Dict.update` copies the dictionary on every call when a nominal
record holding it is built in a `var` loop

Summary:: A loop that owns a value and replaces it with an updated copy
on each step normally updates in place. With a nominal record of two
dictionaries, where a method grows one of them with `Dict.update` and the
other with `Dict.insert`, built in a `var` loop of a function that is
called from two places, the dictionary grown with `Dict.update` is
shared when it grows: each call copies it, with an incref of every entry,
so building n entries is quadratic. Each of these changes alone makes it
linear: `contains` and `insert` instead of `Dict.update`; a structural
record instead of a nominal one; one dictionary instead of two; one
caller of the building function instead of two; a recursive function
instead of the `var` loop.

Reproduction:: `dict-update-sharing/main.roc` (basic-cli 0.28.1) builds
a `Bag :: { rows : Dict(U64, Str), seen : Dict(U64, Bool) }` of n keys
twice per size (`generated(n)` and `generated(n + 1)`, the two callers).
+
[source,sh]
----
roc build main.roc --output=/tmp/dict-update && /tmp/dict-update
----

Expected:: Constant time per `add`.

Actual:: Time per `add` grows linearly with n. Apple M-series, `roc
build` (LLVM, `--opt=speed`), ns per `add` (the first of the two
callers; the second is the same within noise), with each change from the
summary applied alone:
+
|===
| n | as written | `contains` + `insert` | structural record | one dictionary | one caller | recursion

7+| Roc 0.1.0 RC1
| 2,000 | 1,127 | 165 | 156 | 125 | 159 | 192
| 8,000 | 3,886 | 141 | 128 | 86 | 156 | 148
| 32,000 | 16,405 | 157 | 135 | 87 | 152 | 162
| 64,000 | 51,060 | 213 | 136 | 106 | 154 | 189
7+| nightly-2026-11-22-3350b1c
| 2,000 | 1,159 | 172 | 154 | 88 | 139 | 153
| 8,000 | 3,876 | 145 | 119 | 74 | 119 | 121
| 32,000 | 19,529 | 147 | 135 | 79 | 132 | 134
| 64,000 | 66,123 | 150 | 138 | 92 | 135 | 147
|===
+
`sample` of the `--debug` build shows the time in `RocList.reallocate`
-> `memcpy` (from `listReserveForAppend`, the append of the new entry)
and in `roc_builtins_list_set` -> `memcpy`, with increfs of the copied
entries: the dictionary's entry and bucket lists are copied, which
happens only when they are shared.

Suspected mechanism (not confirmed; compiler at 3ff191391f):: In
`Dict.update` (`src/build/roc/Builtin.roc`), the `Missing` branch
returns `dict` itself when `alter` answers `Err(Missing)`, and
otherwise passes the `data` it matched out of `dict` to
`dict_insert_absent_data`. If `dict` is kept alive across `alter`'s call
for the first arm, `data`'s lists are shared when the second arm appends
to them. That would explain why it depends on whether `Dict.update` and
the closure are specialized and inlined together (which the nominal
record, the second dictionary, the two callers and the loop all change),
but a direct loop of `Dict.update` over a plain dictionary stays linear.
Writing the `Err(Missing)` arm as `HashMap(data)` may avoid it in the
builtin.

Engine impact. Every table write records the key's state before its
first write in the table's change record, with `record.update(key, ...)`
keeping the first state. Outside a turn the record grows with the table,
so an app building a table with `Table.insert` in a loop
(`examples/contacts`) copied the record on every insert: in bench/rows
built that way, 0.3 s of mount engine time at 10,000 rows and 53 s at
100,000. Engine patch 0004 records with `contains` and `insert` (it also
takes the table apart with `match`, see <<destructure-sharing>>): 19 ms
and 0.15 s. bench/rows' `--smoke` guards it (2,000 against 18,000 rows
inserted one at a time).
