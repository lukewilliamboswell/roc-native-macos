= The grid stress test

How far the platform scales: an N×N grid of small fixed-size boxes, for N =
10, 32, 100, 316 and 1000 (100 to a million cells). The pointer entering a
cell turns it hot, and a one-shot timer for that cell turns it back 500 ms
later, so a moving pointer leaves a fading trail. Nothing ticks globally;
the live timers are the trail. A reactive UI draws nothing between events,
so this measures three things: how many elements the platform holds, what
one event costs at that size, and what many short-lived timers cost.

*In short:* a hover answers in about 0.2 ms at every size up to 250,000
cells (two engine turns of 0.1 ms or less, no layout), and the trail behaves
at every size. Opening the window is the ceiling: 10,000 cells open in
0.45 s and 177 MB, 100,000 in 4.9 s and 1.2 GB, 250,000 in 22 s and 2.2 GB.
Since stacks of fixed-size cells are placed by frame, Auto Layout is out of
it; what remains is AppKit's cost per `NSView`, which grows with the number
of views (<<where-it-breaks>>). A million cells (N=1000) is not a
reasonable target for one view per cell; see <<ceiling>>.

It is a harness, not an example. The gate's `bench` stage builds it and runs
`run.sh --smoke`: a 4×4 grid and a 12-move sweep, which fails unless the
cells were hovered and every trail timer has cooled. That keeps it from going
stale without putting any load on the gate. The specs beside it,
`tests/specs/grid-20.scm` and `tests/specs/grid-60.scm`, then count the work with the
same bounds at 400 and 3,600 cells: three hovers emit three commands and
create no element, and their three cooling timers cool three cells, so a
turn whose work grows with the cells fails. `--smoke` also reports how
mount and turns scale in time, as a diagnostic that never fails: it mounts
N=20 and N=60 (400 and 3,600 cells) and sweeps 40 moves across each. It
reports it if the larger mount engine time is more
than 27 times the smaller (9 times the cells, so 3 times the linear
expectation; the smaller time is floored at 2 ms; a quadratic mount gives
about 87), or if the hover turns' engine p50 at N=60 is more than 4 times
N=20's (a turn should not grow with the cells; the smaller is floored at
0.1 ms, the host's resolution; before roc-signals#307 the ratio was
about 7 to 9, 0.1 against 0.7 to 0.9 ms, and it is now 1). roc-signals
0.8.0-rc2 (roc-signals#305 to #307) made mount linear and
turns independent of the grid, all by working around compiler behaviour,
and the specs keep the work from regressing silently. `NO_SCALING=1` skips both timings.

== Running it

[source,sh]
----
blueprint run build -- --platform   # the host, once
bench/grid/run.sh                # N = 10 32 100 150 200 316
bench/grid/run.sh 50 70          # other sizes
bench/grid/run.sh --smoke        # what the gate runs
TIMEOUT=600 bench/grid/run.sh 100
----

Each N is a fresh process. N reaches the app as the local storage key
`grid-n`, passed as a launch argument (`-grid-n 316`, Cocoa's argument
domain, read through `ROC_STORAGE_SUITE`), so the mount itself builds the
grid and time to first display is honest. `ROC_BENCH=1` turns on the host's
timings and a sweep, a spec's steps (`ROC_SPEC`), drives the pointer: it crosses
the grid's diagonal in 2N moves (at least 200, at most 2000), one every
10 ms, through the same hit test the mouse uses, then waits for the trail
to cool and prints `stats`. A run still going after `TIMEOUT` seconds (120)
is killed.

`stats` prints, on stdout:

* `views`: every `NSView` in the window, and the peak RSS (`getrusage`);
  `timers-peak` is the most timers alive at once (the trail), and
  `timers-live` those alive now;
* `first-display`: from `main` to the window drawn, with the mount turn's
  engine, apply and layout times and the first forced display;
* per kind of operation (`mount`, `hover`: one pointer move's turns, `timer`:
  one timer's turn), how many and their p50/p95/max in ms for each phase:
  `engine` (the Roc call), `apply` (decoding the commands into views),
  `layout` (the host's `sync`: arranging stacks and fitting the window) and
  `display` (a forced `displayIfNeeded`).

The sweep prints how long its moves took against the plan: a lagging sweep
means turns took longer than the 10 ms between moves.

=== The live HUD

`LIVE=1 bench/grid/run.sh 100` opens the grid with no script: move the mouse
yourself. Under `ROC_BENCH=1` (and only then) the host draws a small panel
over the window's top-right corner, refreshed twice a second from a host
timer, never through the engine, so it does not perturb what it shows. It
is a borderless child window that never becomes key and lets the mouse
through, so it is outside the content's layout and hit testing (and a
`screencapture -l` of the app's window leaves it out). Over the last
second:

* *event→paint*, p50 and p95: from the mouse event's timestamp to the end
  of the forced display that drew its answer, which is what a person feels
  (the window server then composites it on the next refresh, about one more
  frame, which the host cannot see without linking QuartzCore);
* *draws/s*: operations that had something to draw. A reactive UI draws
  nothing when nothing changes, so a still pointer shows `idle`, not a
  frame rate; this counts the host's draws, not the display's refreshes;
* *moves/s* and how many were *lagging* (waited more than a 60 Hz frame for
  the main thread; AppKit itself coalesces moves before the host sees
  them), and engine *turns/s*;
* p95 per operation of engine, apply, layout and display time;
* live timers (the trail), the view count and the hover targets (recounted
  after a layout), the current RSS (`task_info`), and the time to first
  display.

The grid size is fixed per launch: relaunch at another N rather than switch
in the app. A switch would be cheap to write (`Engine.switch` over the
sizes) but measures badly: the engine evaluates every branch's description
at mount (1.2 s for the million-cell one), and remounting takes as long as
the first mount.

== Results

Apple M-series, 8 cores, 16 GB, macOS 26.3, `roc` 0.1.0 RC1, measured
2026-11-23 with engine patches 0001–0003, on a machine also building other
worktrees (load average 3 to 6 for the "after" runs, up to 9 for the
"before" ones), so treat the numbers as ±20%. "Before" is the host at
df14a67, which arranged every stack with NSStackView and drew every box
into a backing store; "after" places stacks of fixed-size children by
frame and gives a box's fill to its layer (this branch). First display is
from `main` to the window drawn, with the mount's engine / apply / layout
time; a hover move is one pointer move's leave and enter turns, p50 / p95
in ms (engine and display are each 0.1 ms or less).

The sweep column is how much longer the driven sweep took than planned
(10 ms a move): the main thread's other work between moves, mostly Core
Animation committing the frame. Before the box drew through its layer, the
N=316 sweep took twice its plan (13.6 s for 6.3 s), with the main thread in
`CA::Transaction::commit` redrawing backing stores.

The steps between "before" and "after", at N=100: placing fixed-size
stacks by frame took the mount's layout from 3.16 s to 0.36 s and RSS from
1.6 GB to 0.61 GB; taking the framed children out of Auto Layout altogether
(no autoresizing constraints) took layout to 0.09 s and RSS to 0.45 GB;
drawing boxes through their layers took RSS to 0.18 GB.

A hover move is engine-bound and tiny at every size: the host's side of a
turn that only repaints is the commands it applies (0.1 ms), a hit test
that searches each framed stack by position instead of trying every child,
and a forced display of the dirty cells (0.1 ms). Nothing walks the views
or nodes per turn: `sync` returns at once for a batch with no structural,
text or layout change, the HUD recounts views only after a turn that laid
the window out, and `stats` counts them only when asked. A turn that does
change structure or text still walks the node tree outside lists once
(`layoutPass`, finding scroll areas); the grid has no such turn.

The trail behaves: the live timers peak at the trail's length (3 at N=10, 8
at N=32, about 22 from N=100 up, for 500 ms of the sweep), never at N², and
fall to 0 once it cools; every cell entered was cooled by its own timer,
and re-entering a hot cell cancels its earlier timer (`watch_latest`).

[#where-it-breaks]
== Where it breaks, and why

Layout on every turn (fixed):: Before 85a0951 every batch, even one that
only changed a cell's fill, ran the host's whole layout pass, which builds
a fresh Auto Layout solver over every view's constraints (2.1 s per hover
at 10,000 cells). A batch that sets only `fill`, `border`, `radius` or
`color` and changes no structure or text skips the pass and is only drawn.

The engine's mount was quadratic (fixed):: Mounting copied the whole
command buffer on every append that grew it (6.4 s of engine time at 10,000
cells). roc-signals 0.8.0-rc2 (roc-signals#305, #306) made it
linear: about 8 µs a cell now (79 ms at 10,000, 0.88 s at 100,000, 1.9 s
at 250,000). The `--smoke` mount-scaling check guards it.

The engine's turn was linear in the grid (fixed):: Each turn copied the
root site's child list (a 2.4 MB `memcpy` at 10,000 cells, 2.5 ms a hover),
because an erased call borrowed the site's captures
(https://github.com/roc-lang/roc/issues/13374[roc-lang/roc#13374]). roc-signals#307 fixed it:
a hover's engine time is 0.1 ms (p50) at every size measured, up to
250,000 cells, and the `--smoke` turn-scaling check guards it.

Auto Layout at mount (fixed):: NSStackView arranged every cell with
constraints, and the first `layoutSubtreeIfNeeded` solved them all: 3.2 s
at 10,000 views, and at 22,500 the solver (`updateConstraintsIfNeeded`,
`NSBitSetFindNext` in CoreAutoLayout) took RSS past 3.4 GB before the
process was killed. A stack whose children all have fixed sizes now places
them by frame (`host/Frames.swift`, rule in `docs/architecture.adoc`),
and the cells it places are not in Auto Layout at all: AppKit gives every
view that translates its autoresizing mask four constraints of its own
(`NSViewSetAutoresizingConstraints`), which alone was 40,000 constraints
and most of the remaining time at 10,000 cells, so an empty box or an inner
framed stack keeps neither. Only the outermost stack of the grid takes part
in Auto Layout, with its total as its content size.

Backing stores (fixed):: Each box drew its fill in `draw(_:)`, so Core
Animation kept a backing store per box: at 100,000 boxes, 99,868 regions
and 1.5 GB (`vmmap`), and seconds of `CA::Transaction::commit` redrawing
them after the mount. A box's fill and solid border are now its layer's
properties (`updateLayer`), with no backing store.

AppKit's cost per view (the wall now):: With the engine and Auto Layout out
of the way, the mount's host time is creating the views, and it grows
faster than the views: apply is 15 µs a cell at 10,000, 25 µs at 100,000
and 65 µs at 250,000. `sample` at N=316 puts about 70% of apply in
`-[NSView initWithFrame:]` → `_commonAwake` →
`-[NSNotificationCenter addObserverForName:object:queue:usingBlock:]`:
every `NSView` registers a notification observer as it is made, and
adding to a registrar that already holds 100,000 observers moves their weak
references (`objc_moveWeak`, `weak_entry_for_referent`). The host cannot
avoid it except by making fewer views. Memory is about 9 KB a cell at
250,000 (12 KB at 100,000): the `NSView` and its `CALayer`, the host's
node, and the engine's site and state. The rest of the mount is the
engine (8 µs a cell) and the window's layout (about 10 µs a cell, mostly
AppKit sizing and positioning the views).

[#ceiling]
== What would move the ceiling, by payoff

. *A canvas or collection element* (`Ui.grid`): one view per visible
  cell, or one view drawing all of them. An `NSCollectionView` (see
  `bench/rows/README.adoc`) makes item views only for the cells in sight
  and reuses them, so a million cells costs the visible few hundred views
  plus one engine row per cell; a canvas (one layer, hit testing by
  arithmetic) costs no view per cell at all. Payoff: the only way to a
  million cells; NSView's per-view cost above rules out one view a cell.
. *Window the engine's rows* (as `table_view`'s `window` allows): build
  only the cells in sight in the engine too, for a grid larger than the
  window. Payoff: engine mount and memory proportional to the visible
  cells.
. *Fewer views per cell*: each cell here is one view (the hover wrapper has
  none); a cell with a label inside a box is two or three. Framed stacks
  already add no constraints, so the cost is the views themselves.
