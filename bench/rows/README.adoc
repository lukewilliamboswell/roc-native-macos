= The rows benchmark

A million simultaneously visible cells is not a realistic interface; a
million rows in a list that shows forty of them is. This harness is that
list: N generated rows (N = 10,000, 100,000 and 1,000,000) in a
`Ui.table_list`, a view-based `NSTableView` that makes views only for the
rows in sight, over an `Engine.table_view` that draws only the rows near
them, with a search field filtering it, a selection shown below the list,
and a "Tick" checkbox that starts an interval changing three rows' values
every 100 ms. With `LIST=every` the list is instead a `Ui.list` of a
`table_view` drawing every row (`Engine.every_row`), as before windowing. It asks one question of
each operation: does it cost what changed (the rows selected, scrolled
into sight, written or filtered in or out), or does it cost N?

The engine patches these results name (0001 to 0006) were this
repository's series on roc-signals, measured as listed. roc-signals
0.8.0-rc2 took all six (roc-signals#305 to #310), and the platform now uses
that release's engine package unpatched.

*In short:* selecting, scrolling and writing rows cost the same at a
million rows as at ten thousand (2–3 ms, 20 ms a screenful; a turn that
writes 3 rows is 0.1–0.3 ms of engine time and 2 ms of host time).
Windowed, a million rows open in 0.3–0.4 s and 370 MB (2.5 s and 1.6 GB
drawing every row), and clearing a filter takes 30–40 ms (2.7 s): see
<<windowed>>. What still costs N is in the engine: building the table and
the view at mount, and every filter keystroke (by design: a new query
rebuilds the view in the size of the table, 12–21 ms at a million). See
<<scaling>>.

It is a harness, not an example. The gate's `bench` stage builds it and runs
`run.sh --smoke`: 200 rows through every phase below, which fails unless
each phase ran and the list holds all 200 rows again once the filter is
cleared. Then the specs beside it, `specs/rows-2000.scm` and
`specs/rows-200000.scm`, count the work with the same bounds at both
sizes (docs/apps.adoc, "Work metrics"): the mount
creates at most 150 rows (one window), five ticks of the interval, each
writing three rows, update at most 15 rows and emit at most 15 commands,
and selecting a row does one turn and one command. A table that drew every
row, or a write whose cost grew with the table, fails them. The timings
that follow are diagnostics, reported and never failing, each comparing
two sizes in fresh processes:
the windowing guard (`window_guard`): the list mounted over 2,000 rows and
over 200,000 must draw the same window (at most 300 rows, from the `stats`
line `bench: list rows N drawn D`) and apply its mount in about the same
time (at most three times the small one's, plus 15 ms); the engine's mount
time is not compared, since building the table and its view is linear in
the rows, windowed or not. A write-scaling check: the tick's engine p50 at
200,000 rows must be at most 5 times its p50 at 2,000 (it is about 1;
before engine patches 0004 and 0005 it was 38). And an insert-loop check:
it builds 2,000 and 18,000 rows with `Table.insert` in a loop
(`-rows-build insert`, the faster of two runs each) and fails if the
larger mount's engine time is 25 times the smaller's or more: linear is
about 9, and before engine patch 0004 it was about 96.

== Running it

[source,sh]
----
blueprint run build -- --platform   # the host, once
bench/rows/run.sh                # N = 10000 100000 1000000
bench/rows/run.sh 50000          # other sizes
bench/rows/run.sh --smoke        # what the gate runs
LIST=every bench/rows/run.sh     # a Ui.list drawing every row
----

Each N is a fresh process. N reaches the app as the local storage key
`rows-n` (`-rows-n 1000000`, as `bench/grid` passes `grid-n`), so the mount
itself builds the table (keyed once from a list; `-rows-build insert`
inserts the rows one at a time instead). `ROC_BENCH=1` turns on the host's timings, and a
session of spec steps runs one phase after another, each named with `(phase "NAME")` so
`stats` reports its operations apart (`event/select`, `scroll/scroll`, …):

select:: `(select (list-row 1))`, then rows 2, 3, 10 and 4: the user selecting rows (an
event turn each: the selection cell and the text below the list).
scroll:: `(scroll K)` eight times a screenful down from the top, then to the
middle, near the end and back to the top. A scroll is not an engine turn:
it is the table tiling, making the new rows' views from their nodes, and
drawing, timed as one `scroll` operation.
tick:: "Tick" on for a second: ten interval turns, each writing three rows
of the table (`Table.update`), which are on screen.
filter:: typing `echo e` a letter at a time into the search field: each
keystroke is a new query.
clear:: emptying the field: every row comes back.

A run still going after `TIMEOUT` seconds (300) is killed.

What windowing changed:

* *Mount, a filter that lets many rows in or out, and memory* cost the
  window: the host applies the mount of a million-row list in 8 ms, as it
  does ten thousand (the guard checks this), and clearing the filter
  applies in 3 ms. The engine's share is the table and view build at mount
  (151–211 ms at a million, from 1.6–2.1 s) and the query's rebuild on a
  filter change (8–19 ms at a million): drawing a million rows and
  diffing a million-row window were most of the old engine time.
* *Scrolling* is unchanged for the rows in sight, plus a window move each
  time the visible rows come within half a screen of the window's edge:
  one turn removing and drawing about a screenful of rows (engine 0.2 ms,
  apply 1–2 ms; its layout reloads the rows in sight that were
  placeholders). A jump far down the list (`scroll:500000`) shows
  placeholder rows until that turn, on the next pass of the run loop.
* *A table write* (Tick) cost about half before engine patches 0004 and
  0005: the `table_view` over every row was half of it, and the rest the
  table's own write. With them it is under a millisecond either way (see
  <<combined>>).

[#scaling]
== What scales with what

Proportional to what changed (good)::
* *Select*: one event turn, 0.0–0.2 ms of engine and 2 ms of host layout
  (`sync` fitting the window after the text below the list changed), at
  every N.
* *Scroll*: about 0.85 ms per row scrolled into sight, at every N: the
  host builds the row's nodes from its template (`materialize`), makes its
  views and the table sizes it (`usesAutomaticRowHeights`). Rows already
  seen keep their cell views.
* *A written row's repaint*: the host's part of a tick is 2 ms whatever N.
* *Writing the table.* A turn that writes three rows (`cells.rows.update`
  with three `Table.update` calls) costs 0.1–0.3 ms of engine time at
  every N. It cost 0.5 ms at 10,000 rows, 6.6 ms at 100,000 and 79 ms at
  1,000,000 until engine patches 0004 and 0005: every `Table.update` copied
  the table's rows (`TableCore.write` took the table apart with a
  destructuring statement, which the compiler leaves shared), the first
  write of each turn copied them again (the cell's lens), and the root's
  pass read its block shared, so the `table_view` copied its per-row
  columns (marks, a hole column, the shown column: 196 MB at a million
  rows) on every turn. The reader was never the cost. See
  xref:../../patches/roc-compiler/README.adoc#destructure-sharing[destructure-sharing].
* *Building a table by inserting rows one at a time.* Inserting the rows
  in a `var` loop with `Table.insert`, as `examples/contacts` does, was
  quadratic: the mount's engine time was 0.3 s at 10,000 rows, 4.6–5.4 s
  at 30,000 and 53 s at 100,000, because every insert copied the table's
  change record (`Dict.update`, a compiler issue:
  xref:../../patches/roc-compiler/README.adoc#dict-update-sharing[dict-update-sharing]).
  Since engine patch 0004 it is 19 ms, 48 ms, 0.15 s and 1.8 s at a
  million (`-rows-build insert`), against 13 ms, 0.11 s and 1.45 s for
  `Table.from_list`, which the harness still uses by default.

Proportional to N, in the engine (reported for roc-signals)::
* *A filter keystroke*: a new query rebuilds the view in the size of the
  table, as the engine documents (`table_view`): drawing every row, 1.1 ms
  at 10,000, 11 ms at 100,000, 143 ms (p95 0.7 s) at a million; windowed,
  0.3, 1.8 and 12–19 ms, the rebuild alone (a `keep` per row and a sort of
  what is kept). This stays linear: a new filter must look at every row.
* *Every row the query keeps is drawn* (`Engine.every_row`, `Ui.list`):
  the mount and a filter that lets many rows in or out emit one `INST` or
  `REMOVE` per row, so clearing the filter at a million rows is 1.8 s of
  engine time and 0.8 s of host apply. `Ui.table_list` draws only a
  window: <<windowed>>.

Proportional to the rows that changed, in the host [[host]]::
The host's per-row work at mount and on a filter is now a small node per
row and nothing else; before this branch it was most of the time:
* A list row from a template was cloned into its whole node tree when the
  engine inserted it; it is now only its hole values until the table first
  shows it (`Host.materialize`), and `TEXT`/`HATTR`/`HPROP` update those
  values (the ticking rows are written without building anything).
* `Node.parent` was weak: every node got a weak-reference side table and
  slow reference counting, a third of the million-row mount. It is strong,
  and `forget` breaks the cycles.
* Inserting a child before another searched and shifted the parent's whole
  child array (quadratic when a cleared filter lets a million rows back in
  before their neighbours); inserts and removals now wait and are merged in
  one pass when the children are next read.
* Every inserted row queued its list for a refresh (a million entries); a
  node is now queued once per layout pass, and a reload keeps only the
  shown rows' cell views instead of hashing every row.

What is left that touches N rows in the host is releasing removed rows'
nodes and the `rows` array a reload rebuilds, both in the rows changed. A
small change (64 rows or fewer, applied as table row updates) still finds
each row's index by a scan of the list's rows, up to 64 scans of N.

== Recommendations, by payoff

. *Window the list to the rows in sight.* Done: `Ui.table_list`, see
  <<windowed>>.
. *Make a table write cost the rows written.* Done: engine patches 0004
  and 0005, see the writing bullet above.
. *Make `Table.insert` in a loop linear.* Done: engine patch 0004 (a
  table write records its key without `Dict.update`).
. *A `Ui.grid` over `NSCollectionView`* (not built; evaluated here). The
  native virtualised grid: `NSCollectionView` with a flow or grid layout
  makes item views only for the visible items and reuses them as they
  scroll, as `NSTableView` does for rows, and with a fixed item size it
  lays items out by arithmetic, no Auto Layout per item. It fits the
  host's list machinery closely: each `ui-grid` child is an item (a
  template row, built lazily as list rows are), engine inserts, removes
  and moves become `insertItems`/`deleteItems`/`moveItem` inside
  `performBatchUpdates`, a large batch is `reloadData`, and selection is
  `selectionIndexPaths`. With the windowing above it is also how a grid of
  a million cells could exist (`bench/grid`: one `NSView` per cell costs
  9–12 KB and AppKit's per-view registration grows with the views). Costs:
  `Ui.grid` props (item width and height, spacing, selection), the
  `ui-grid` element and docs; new linker symbols for `NSCollectionView`,
  `NSCollectionViewItem` (a subclass: its metaclass) and a layout class,
  and index paths through `NSIndexPath` and `NSSet` rather than Swift's
  `IndexPath`/`Set<IndexPath>` bridging, which would bring overlay
  symbols into the catalog; hover and hit testing per visible item as
  today. Payoff: large for photo-grid or icon-grid apps; it replaces
  "one view per cell" with "one view per visible cell".
