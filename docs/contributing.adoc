= Contributing

This chapter is for people changing the platform from a checkout: building
it, running and driving its examples, passing the check gate, bundling it and
releasing it. App authors need none of it; they work from a release, as
xref:apps.adoc#get-started[Build an app] describes. The repository's rules are
in `AGENTS.md`; xref:architecture.adoc#how-it-fits-together[Architecture]
explains the design.

[#build-the-platform]
== Build the platform

Building the platform itself (not an app: an app needs only Roc, on any
system) needs Apple silicon macOS, Xcode, `python3`, and a Roc compiler
installed as `roc`: a current nightly, or 0.1.0 RC1. An Apple silicon Mac
cross-compiles the Intel host as well; CI builds and runs everything on an
Intel Mac too (xref:contributing.adoc#intel-macs[Intel Macs]). The repository follows
https://github.com/lukewilliamboswell/roc-automation[roc-automation], and
https://github.com/lukewilliamboswell/roc-blueprint[Blueprint] 0.13.0
provides the rest of the environment.

[source,sh]
----
blueprint run build                  # Swift host, linker stubs, every example
blueprint run build -- counter       # one example, after the platform is built
blueprint run build -- --platform    # only the platform's native inputs
./examples/counter/counter      # or stopwatch, todos, http-fetch, file-inspector, gallery, contacts, about
open examples/counter/counter.app
----

The build is `scripts/build.roc`, which builds examples with the `roc` on
PATH, or `$ROC`. Building the platform is two steps over committed inputs:

. *Host.* `swiftc` compiles `host/*.swift` for each target, with the
  committed glue `host/roc_swift_abi.h` as its bridging header and an
  explicit `-target` (`arm64-apple-macos15.0`, `x86_64-apple-macos15.0`),
  object by object under `build/host-<target>`, and `libtool -static -D`
  archives them into `platform/targets/arm64mac/libhost.a` and
  `platform/targets/x64mac/libhost.a`, with framework autolinking and
  `FORCE_LOAD` symbols off. `platform/targets/x64v1mac/libhost.a` is a copy
  of the Intel one. The same commit and Xcode build the same bytes on any
  checkout path and either kind of Mac, so each host is fingerprinted (its
  target, its sources, the glue header, the recipe, swiftc and Xcode,
  recorded in `libhost.fingerprint`) and a current one is reused. `build --
  host --reproduce` builds each twice and compares.
. *Linker stubs.* The macOS TAPI stubs in `platform/targets/macos-sysroot`,
  one set for both architectures, come from the linker-input release that
  `link-inputs.lock.json` selects, verified by size and SHA-256, and each
  host's references are audited against what `host/interfaces.json`
  exports for its architecture, then the system imports of the `roc`
  compiler's run shims, which `roc main.roc` links the host with, against
  the catalog's `run_shim` for the architecture of that `roc` (see
  xref:architecture.adoc#linker-inputs[Linker inputs]). A nightly whose
  shims import a symbol the catalog lacks fails the build until a reviewed
  catalog edit adds it, with its evidence, to its library and to
  `run_shim`; that edit is a new linker-input release.

The glue (`host/roc_swift_abi.h`, `host/RocGlue.swift`) is generated by
`glue/SwiftGlue.roc` and committed, so the host never runs `roc glue` and a
change to the interface is a reviewed diff. The `glue` stage of the check
regenerates it with the `roc` on PATH and fails if it differs; `blueprint run
build -- glue` rewrites it. Never edit it by hand. A new nightly that changes
it fails every pull request until the glue, and any host change it needs,
are updated in one pull request. The outputs of the build are not committed.

CI and releases build the host with Xcode 26.3 (Swift 6.2.4), selected by
`.github/actions/setup-xcode`. The Swift version decides which Swift runtime
symbols `libhost.a` references, and so what the stub audit accepts: Xcode
16.4's Swift 6.1, the runner image's default, references four that Swift 6.2
inlines. To move to another Xcode, change the action's two defaults, run the
check gate with that Xcode, and catalog any symbol the audit names.

Each example is built twice over: the bare binary, and a minimal `.app`
bundle beside it (`Contents/MacOS/<name>` and an `Info.plist` with
`CFBundleIdentifier` `dev.roc.native.<name>` and `LSMinimumSystemVersion`
15.0, the host's deployment target). Launched from the bundle, AppKit has a
bundle identifier, so it no longer warns that it cannot index window tabs.
The two keep separate `UserDefaults` domains (`todos` versus
`dev.roc.native.todos`), so they do not share saved values.

[#run-the-examples]
=== Run the examples

The examples under `examples/` are apps that name the platform by its path in
the checkout, `pf: platform "../../../platform/main.roc"` from each
example's `src/main.roc`, so they always build
against the working tree and may use what no release has yet. A release's
examples archive is a copy of them whose headers name that release's bundle
(`release -- archive`, see xref:contributing.adoc#releasing[Releasing]);
committed examples are never rewritten. `blueprint run build` builds every
example as `examples/<name>/<name>` and `examples/<name>/<name>.app`, and
xref:contributing.adoc#driving-an-app[Driving an app] runs them unattended.
A new example needs at least one spec (see
xref:contributing.adoc#specs[Specs]), a tile in the
README's examples grid with its demo (see
xref:contributing.adoc#demos[Demos]), and a row in
xref:apps.adoc#the-examples[The examples].

=== Blueprint tasks

[cols="2,3",options="header"]
|===
| Task | Does

| `blueprint run check` | the pull-request gate; `check -- STAGE...` runs the named stages
| `blueprint run build` | `scripts/build.roc`: host, stubs and every example; `build -- counter` for one, `build -- glue` to regenerate the glue
| `blueprint run link-inputs` | `scripts/link_inputs.roc`, the producer of the linker-input release: `-- build DIR`, `-- stubs DIR`, `-- fingerprint`
| `blueprint run test` | `roc test` on the platform root and every example
| `blueprint run examples` | every example's specs; `examples -- --update` rewrites their dumps and lowers their allocation bounds
| `blueprint run bundle` | the platform bundle, in `build/platform/` (see xref:contributing.adoc#the-bundle[The bundle])
| `blueprint run release` | the release steps after the bundle: `tool`, `archive`, `test`, `notes` and `bump` (see xref:contributing.adoc#releasing[Releasing])
| `blueprint run workflow` | the workflows' steps that ask GitHub or hand values to later steps (`scripts/workflow.roc`): `validate`, `select`, `download`, `files`, `summary`
| `blueprint run docs` | this manual as a website, Markdown and `roc-native-macos.pdf`, in `.docs-out/`, with roc-automation's roc-docs renderer
| `blueprint run tooling-version` | the scripts' compiler version
|===

`.github/workflows/docs.yml` runs `blueprint run docs` on every pull request
and deploys `.docs-out/site` to GitHub Pages from `main`. The renderer takes
a subset of AsciiDoc and refuses what it cannot render, such as a table too
wide for the PDF page, so a manual change is checked by building it.

=== Two compilers

`roc`, the latest Roc nightly, checks, builds and tests the platform, the
glue, the examples and the `macos.roc` tool (`cli/`). It is never pinned: CI
installs the nightly of the day, and a contributor installs a current nightly
(or RC1) as `roc`.
`roc-stable`, which `Blueprint.roc` pins to `nightly-2026-11-22-3350b1c`,
runs the scripts under `scripts/`, and only those scripts name it in their
headers (`roc: "<tag>"`). Format the scripts with `roc-stable fmt`.

[#the-bundle]
== The bundle

App authors name the platform by the URL of a bundle:
`app [main] { pf: platform "https://…/<hash>.tar.zst" }`. `blueprint run
bundle` (`scripts/bundle.roc`) makes that bundle:

. It builds the platform's native inputs (`scripts/build.roc -- --platform`),
  unless `--prebuilt` is given.
. It stages, under `build/bundle-stage/`, the tracked `platform/*.roc`
  modules, `targets/arm64mac/libhost.a`, `targets/x64mac/libhost.a` and its
  copy `targets/x64v1mac/libhost.a`, the generated
  `targets/macos-sysroot/` stubs, `LICENSE` and `THIRD_PARTY_LICENSES.md`.
  The stubs are the catalog's generated TAPI files, not Apple SDK files.
. It runs `roc bundle` there with `main.roc` first, which writes one
  content-addressed `<hash>.tar.zst` to `build/platform/` (or
  `--output-dir DIR`), and prints its size and SHA-256.

`blueprint run bundle -- --test` then checks the bundle the way an author
uses it. It copies the bundle to `build/bundle-test/served/` and serves that
on localhost (Roc accepts `http` URLs for localhost only), makes the
`macos.roc` tool there naming the served URLs (`release -- tool`, see
xref:contributing.adoc#the-tool[The tool]), and with an empty package cache
(`XDG_CACHE_HOME`) runs `roc macos.roc init my-app`, then `roc macos.roc
build`, `roc macos.roc test` (the starter's `expect`s and specs)
and `roc macos.roc fuzz --check` (its roc-fuzz targets) in
`build/bundle-test/my-app/`, and packages it twice. It also builds and tests
`examples/about`, its one-file `main.roc` copied to `src/main.roc` where
the tool reads it, with its assets, through the tool, and runs one of its specs under
`roc macos.roc dev`. The `bundle` stage of `check` does the same with
`--prebuilt`. The empty cache means basic-cli and the platform's own
dependency (roc-parser) are downloaded from GitHub on every run.

To build an app outside the checkout against a local bundle, serve
`build/platform` and name the localhost URL in the app's header. The bundle's
name is its content hash, so the URL changes whenever the bundle does. An app can also name a checkout's platform by a relative
path, `platform "../roc-native-macos/platform/main.roc"`, once
`blueprint run build -- --platform` has built its native inputs; Roc rejects an
absolute platform path.

A release publishes the bundle under
`releases/download/<version>/<hash>.tar.zst`; see
xref:contributing.adoc#releasing[Releasing].

[#the-tool]
== The tool

`macos.roc` is the app author's tool: `init`, `build`, `run`, `dev`, `test`,
`fuzz` and `package`. It
is a package, `cli/`, on basic-cli, which a release bundles and names from a
small launcher app, `macos.roc`, that the author downloads (the same model as
roc-native-android's `android.roc` and roc-signals' `signals.roc`):

[cols="1,3",options="header"]
|===
| Module | Does

| `cli/main.roc` | the package root, exposing `MacOS`
| `cli/MacOS.roc` | the command line: parsing, `help` and `COMMAND --help`, and every failure put into one sentence (`explain`; exit code 2 for misuse)
| `cli/Init.roc` | `init`: the starter scaffold (`examples/starter`), never overwriting a file
| `cli/App.roc` | the app's root module (`src/main.roc`), and `build` and `run`: `roc build --target=arm64mac` and `--target=x64mac`, joined into the universal `.macos/<name>` (or with `--target` one of them alone), then `<name>.app` with its `Info.plist`
| `cli/Universal.roc` | the universal (fat) Mach-O file, written byte for byte as `lipo -create` writes it, with no Apple tool
| `cli/Cases.roc` | `test`: `roc test` on the root module, then each `specs/<name>.scm` run against `.macos/<name>`, built for this Mac's own target alone
| `cli/Fuzz.roc` | `fuzz`: `roc build --fuzz fuzz/main.roc` into `.macos/fuzz`, then each roc-fuzz target it lists, run or (`--check`) checked
| `cli/Spec.roc` | the spec language: parsing, lowering to the host's `ROC_SPEC` steps, judging what the host observed, and `--update`'s rewrite of the dumps and allocation bounds; pure, shared with the scripts
| `cli/SpecRun.roc` | one spec run against a built program, shared with the scripts
| `cli/Bundle.roc` | generated: the release, its platform URL, the Roc that tested it, and the scaffold
|===

`build` writes files and runs `roc`, nothing else, so it works on any system:
Roc's linker signs the program ad hoc (`codesign -dv` shows
`adhoc,linker-signed`), and the `.app` is a directory and a plist. It always
names its targets, `--target=arm64mac` and `--target=x64mac`, and joins the
two programs itself (`Universal`) rather than with `lipo`, which only a Mac
has. Each slice is copied byte for byte, so the linker's signature of each
still holds, and `package` seals the universal program as it sealed a thin
one. With `--target` it builds that target alone (`Native`), the thin
program `test` also builds for the Mac it runs on. `run`, `dev` and `test`
need a Mac, either kind, and say so elsewhere.

`cli/Bundle.roc` is generated by `scripts/src/Release.roc`. The checked-in
copy is for a checkout: version `development`, importing the scaffold (every
tracked file of `examples/starter`, its icon as bytes) from the working
tree, so `roc test cli/main.roc` works. A release generates its own, importing
copies staged under `scaffold/`. The `tool` stage of `check` fails when the
checked-in copy is not what the script generates (when a file is added to
the starter, say); `blueprint run check -- tool --update` rewrites it. The
starter is an example like the others, so `check` builds it, runs its
`expect`s, checks its fuzz targets' examples and runs its specs;
change what `init` writes by changing it.

A script cannot import a module outside `scripts/`, so
`scripts/src/Spec.roc` and `scripts/src/SpecRun.roc` are byte-identical
copies of `cli/Spec.roc` and `cli/SpecRun.roc`, which the `tool` stage
checks. Change the one in `cli/`, then copy it over.

`blueprint run release -- tool VERSION DIR` makes the tool for the platform
bundle in `DIR`: it stages `cli/` with the release's `Bundle.roc`, the
scaffold and the notices under `build/tool-stage/`, runs its `expect`s,
`roc bundle`s it into `DIR/macos-<hash>.tar.zst` (the prefix keeps it apart
from the platform's bundle), and writes `DIR/macos.roc` naming it.
`--base-url URL` names the assets at `URL` instead of the release's download
URL, to try a release locally:

[source,sh]
----
blueprint run bundle -- --prebuilt --output-dir /tmp/rel
python3 -m http.server 8787 --bind :: --directory /tmp/rel &
blueprint run release -- tool 0.0.1-dryrun /tmp/rel --base-url http://localhost:8787
cd "$(mktemp -d)" && curl -LO http://localhost:8787/macos.roc
roc macos.roc init my-app && cd my-app && roc macos.roc run
----

[#driving-an-app]
== Driving an app

A spec drives the real controls through the same action methods AppKit
calls. Its steps and the `ROC_*` variables are app-author material, listed
in xref:apps.adoc#steps[Steps] and
xref:apps.adoc#environment-variables[Environment variables]; when the host's
steps or variables change, update that chapter. To drive an example built in
a checkout by hand, lower a spec's text with `scripts/lower_spec.roc` into
`ROC_SPEC`; `(live-effects)` lets its requests and timers run for real:

[source,sh]
----
ROC_SPEC="$(roc-stable scripts/lower_spec.roc -- '(test "t" (steps (fill (text-field) "Buy milk") (submit (text-field)) (expect-dump _)))')" \
  ./examples/todos/todos
ROC_TRACE=1 ROC_SPEC="$(roc-stable scripts/lower_spec.roc -- '(test "t" (setup (live-effects)) (steps (fill (text-field) "https://example.com") (submit (text-field)) (wait 3000) (expect-dump _)))')" \
  ./examples/http-fetch/http-fetch
----

The run prints each expectation's observation on standard output (`@3 obs`,
then its lines). The bench harnesses drive their timed sessions the same way.

[#specs]
=== Specs

Every example has at least one spec, beside it as an app's are:
`examples/<example>/specs/<name>.scm` (xref:apps.adoc#test-an-app[Test an
app]). Files a spec uses, such as one it opens or drops, live in the
example's `specs/fixtures/`, and its steps name them relative to the
example. `blueprint run examples` runs each spec from the example's
directory against the built app (`EXAMPLES="todos workers"` runs only
those examples'), with a 120-second deadline. A new example needs a spec:
write it with `(expect-dump _)` where a dump helps, run
`blueprint run examples -- --update`, and review the dumps it wrote before
committing them. The `specs` stage of `check` parses every spec, on any
system. The examples' specs and an app's (`macos.roc test`) are run by the
same modules, `cli/Spec.roc` and `cli/SpecRun.roc`, which the scripts copy
byte for byte, so `roc macos.roc test` in an example's directory runs the
same specs.

[#demos]
=== Demos

The README's tiles, `docs/images/<example>.gif`, are recorded from the
built examples. Each example's `examples/<example>/demo.scm` is its demo: a
spec in the same grammar as `specs/`, whose first step is `(window)` and
whose `(live-effects)` lets timers tick and requests go out in real time,
paced with `wait` so a person can follow it. It is not one of the
example's specs, since its timing is real, but the `specs` stage parses it.
After `blueprint run build`:

[source,sh]
----
roc-stable scripts/record_demos.roc                   # every example with a demo.scm
roc-stable scripts/record_demos.roc -- counter todos  # the named ones
----

`scripts/record_demos.roc` runs each example with its steps in the light
appearance, reads the window's number from its `(window)` step,
and takes a frame of that window every 100 ms with
`screencapture -l<number> -o -x` until the spec ends. A capture names the
window, so the app never needs focus and windows above it never show.
ffmpeg then scales the frames to 400 pixels wide on the window's backdrop,
drops repeated frames and frames caught mid-resize, and writes a looping GIF
with one palette; it prints each GIF's size, frame count and length. Keep a
tile under 400 KB.

Recording needs ffmpeg on PATH and the Screen Recording permission for the
terminal (System Settings, Privacy & Security), so it is not part of the
check gate; its pure parts (`scripts/src/Demo.roc`) are tested in the
`scripts` stage. While it records it serves the checkout at
`http://127.0.0.1:8737/`, which the http-fetch demo fetches so it never
depends on the network; the file-inspector demo drops files from
`/usr/share/dict`, so no local path shows in its tile. Its frames are left in
`build/demos/<example>/`. Review a new GIF before committing it.

== The check gate

`blueprint run check` (`scripts/check_all.roc`) is the pull-request gate, the
same one CI runs on `macos-15`, and in part on `macos-15-intel`
(xref:contributing.adoc#intel-macs[Intel Macs]). Its stages, in order:

[cols="1,3",options="header"]
|===
| Stage | Checks

| `pins` | `roc-policy check` (roc-automation's source-policy utility) with `repository_policy` from `Blueprint.roc`: the scripts pin `roc-stable`, nothing else pins a compiler, and every example's `src/main.roc` names `../../../platform/main.roc`
| `engine` | the engine facades `platform/{Engine,Layout,Wire,Worker}.roc` are what the engine package `platform/main.roc` names gives (`build -- engine --check`; xref:contributing.adoc#engine-package[The engine package])
| `fmt` | `roc fmt --check` over the platform, glue, examples and tool, and `roc-stable fmt --check` over the scripts
| `scripts` | the scripts' `expect` tests
| `specs` | every spec under `examples/` and `bench/` parses
| `tool` | `cli/Bundle.roc` is current (`tool --update` writes it), `scripts/src/{Spec,SpecRun}.roc` copy the tool's, and `roc test cli/main.roc`
| `glue` | the committed glue is what `glue/SwiftGlue.roc` generates with the `roc` on PATH (`build -- glue --check`)
| `build` | `scripts/build.roc` with the `roc` on PATH
| `test` | `roc test` on `platform/main.roc` and every example (its `src/main.roc`, with the starter's logic package), and for an example with `fuzz/main.roc` (the starter) its roc-fuzz build and `check` on every target
| `examples` | every example's specs
| `bench` | every harness under `bench/`, built and run at a token size (`bench/<name>/run.sh --smoke`) so it never goes stale, failing unless the run does what it measures; then its specs, `bench/<name>/specs/*.scm`, which count a turn's work with the same bounds at two sizes: a hover or a cooling timer at N=20 and N=60 cells, a tick writing 3 rows and a selection at 2,000 and 200,000 rows. The harnesses' timing ratios are reported as diagnostics and never fail
| `matrix` | every build an author can ask `roc build` for, of `examples/arith` (the library calls 128-bit, `Dec` and float arithmetic lower to) and `examples/workers` (worker threads, and a crashed job's unwind): each built with every `--opt` (`speed`, `size`, `dev`, `interpreter`) and `--specialize` (`yes`, `no`) for this Mac's own target and run against one spec (`arith`'s `rows`, `workers`' `crash`), then `arith` with every `--opt` but `interpreter` (which builds only for the native target) for the other Mac targets, each linked, and run too where this Mac runs it: `x64v1mac` under Rosetta on Apple silicon, natively on an Intel Mac. Programs go to `build/matrix/`. It takes about 10 minutes on an M-series Mac, most of it `workers` with `--specialize=yes` (`TODO(slow-lambda-sets)`). A missing system symbol fails here first, so take it into `host/interfaces.json` with its evidence
| `bundle` | the bundle from the `build` stage's inputs, and its consumer test: `macos.roc` `init`, `build`, `test`, `fuzz --check` and `ci package` against it
|===

`check -- STAGE...` runs only the named stages. On a terminal the result
words (`PASS`, `FAIL`, `SKIP`, `passed`, `failed`) are coloured; `NO_COLOR`
or a redirected output leaves them plain, and the word is always printed.

[#intel-macs]
=== Intel Macs

The platform's targets are `arm64mac` and `x64mac`, and `x64v1mac`, Roc's
baseline Intel target, which a machine whose CPU does not report x86-64-v3
(Rosetta, and some virtual machines) builds for natively. Nobody needs an
Intel Mac to work on it: an Apple silicon Mac cross-compiles the Intel host,
and the linker stubs serve both. CI runs what depends on the CPU on GitHub's
Intel runner, `macos-15-intel`, with the hosts the `host` job
cross-compiled:

* `ci.yml`'s `Check on an Intel Mac` job runs `scripts/check_all.roc --
  scripts tool glue build test examples matrix bundle`: the glue the Intel `roc`
  generates (identical to Apple silicon's), the stub audit of both hosts and
  of the Intel `roc`'s own run shims, every example's `expect`s, every
  example built natively and its specs run, the counter's through
  `roc src/main.roc` too, the build matrix with its `x64mac` and
  `x64v1mac` builds run natively (the only place an `x64mac` build runs:
  Rosetta has no x86-64-v3), and the bundle's consumer test, which inits the
  starter app and whose `macos.roc` builds a universal app and runs its
  Intel half. roc-fuzz has no Intel Mac target (only `arm64mac` and
  `x64musl`), so on Intel the `test` stage does not check the starter's
  fuzz targets and the consumer test skips `macos.roc fuzz --check`; the
  Apple silicon `Check` job runs both.
* `link-inputs.yml`'s `intel` job links and runs every example against a
  linker-input candidate before it can be published.
* `release.yml`'s `Intel` job tests the candidate's files natively, and
  `cross-run` runs the cross-compiled Intel programs and universal apps.

Blueprint's dev environment is Apple silicon only: roc-policy and roc-docs,
which it locks, have no `x86_64-darwin` build. So the Intel jobs install the
two compilers themselves (`.github/actions/setup-roc-tooling`: the tooling
release as `roc-stable`, the nightly as `roc`) and run the scripts with
`roc-stable`, leaving out the `pins`, `engine`, `fmt` and `bench` stages,
whose results do not depend on the CPU.

To try the Intel side on an Apple silicon Mac, put the Intel `roc` nightly
(`roc_nightly-macos_x86_64-…`) first on PATH as `roc`; Rosetta runs it, and
`roc-stable scripts/check_all.roc -- build examples` builds every example for
`x64v1mac` and runs its cases under Rosetta.

[#engine-package]
== The engine package

The engine is roc-signals' standalone engine package, which
`platform/main.roc` names in its `packages` as `engine`. A platform cannot
list a package's module in its `exposes`, so `platform/Engine.roc`,
`Layout.roc`, `Wire.roc` and `Worker.roc` re-expose the package's modules
of the same names: each aliases every type and forwards every value of the
module's block, under the package's doc comments, and apps keep writing
`import pf.Engine`. They are generated by `blueprint run build -- engine`
(`scripts/src/Facade.roc`) and committed; never edit them. The platform root
reaches the engine's host contract through the package's `EngineHost`.

To take a newer engine, change the `engine` URL in `platform/main.roc` to
the release's engine package, run `blueprint run build -- engine`, review
the facades' diff, and update the version in
xref:architecture.adoc#how-it-fits-together[How it fits together],
`THIRD_PARTY_LICENSES.md` and `sbom/composition.json`, all in the same
commit. A change the platform needs in the engine is made in roc-signals
first.

A cost that turns out to be the compiler's is not patched here. It gets a
standalone reproducer and a write-up in `patches/roc-compiler/`, listed in
its `README.adoc` for reporting to roc-lang/roc.

[#releasing]
== Releasing

`.github/workflows/release.yml` builds what a release contains once, tests
those exact bytes, and publishes them once, as roc-automation's platform
release workflow prescribes. A maintainer dispatches it from `main` with a
version such as `0.0.1` or `0.1.0-rc1`; the tag it creates is the bare
version, with no `v`. A pull request that touches the platform, the host, the
examples, the scripts, the notes or the workflow runs it as a dry run under
`0.0.1-dryrun`, which publishes nothing.

[cols="1,3",options="header"]
|===
| Job | Does

| Validate | resolves the Roc nightly for the whole run and the latest final release, and refuses a version that is not SemVer, a dispatch off `main`, an existing tag, or a missing `docs/releases/<version>.adoc`
| Build (`macos-15`) | selects the pinned Xcode, checks the version against the latest final release (`release -- bump`, below), runs `blueprint run check` (the whole gate, which builds the host and runs every spec against it), bundles that same `libhost.a` (`bundle -- --prebuilt`), makes the `macos.roc` tool naming it (`release -- tool`), writes the examples archive (`release -- archive`), builds every archived example against the bundle served on localhost with an empty package cache and runs every spec, then with the served `macos.roc` creates, builds and tests an app (`release -- test`), binds the SBOM sidecars of the bundle, the examples archive and the tool (`actions/sbom-sidecars`, from `sbom/composition.json`, `sbom/examples.json` and `sbom/tool.json`) and renders the notes (`release -- notes`)
| Intel (`macos-15-intel`) | the same candidate on an Intel Mac: builds every archived example natively against the served bundle and runs every spec, then with the served `macos.roc` creates, builds (universal) and tests an app (`release -- test`)
| Cross-compile (`ubuntu-24.04`, `ubuntu-24.04-arm`, `windows-2025`) | with only Roc installed and no checkout, serves the candidate on localhost, builds every archived example with `--target=arm64mac` and `--target=x64mac`, and with `macos.roc` creates the starter app with `init` and builds `starter.app`; each program must be a Mach-O executable for its CPU, and each `.app`'s a universal one. It also records what `roc build` without `--target` does there.
| Run the cross-compiled apps (`macos-15`, `macos-15-intel`) | on each Mac, runs every spec against each system's programs for that Mac and the universal `.app`s, the starter's against the `starter.app` `init` made (`release -- cross-run DIR CROSS TARGET`)
| Attest | build-provenance attestations for every file, and SBOM attestations for the bundle, the examples archive, the tool's package and `macos.roc`, exported as `<file>.intoto.jsonl`
| Publish (`release` environment) | checks out nothing and runs no repository code: `actions/publish-release` stages a draft at the tested commit, downloads every asset back and compares it with the tested file, then publishes
|===

A release holds the bundle `<hash>.tar.zst`, `macos.roc` and the tool's
package `macos-<hash>.tar.zst`, `roc-native-macos-examples-<version>.zip`
(every example naming the release URL, with its specs and
fixtures), each with its SBOM documents (`.spdx.json`, `.spdx-2.3.json`,
`.cdx.json`, `.sbom-manifest.json`), and the exported attestations. The
notes are `docs/releases/<version>.adoc` with `{platform-url}`,
`{examples-url}` and `{launcher-url}` (`macos.roc`) filled in, followed by
the compilers, the Xcode and Swift versions, and every file's SHA-256.

The bundle's hash depends on every byte it holds, `libhost.a` included, so
the URL is known only once the build job has run. It is printed at the top of
that job's summary, in the notes, and in the dry run's summary. The host is
reproducible: the same commit, Xcode and catalog build the same `libhost.a`
on any checkout path, so a rebuild of the tested commit names the same
bundle.

`release -- bump VERSION LATEST URL` runs `roc bump --old URL --expect
VERSION platform/main.roc` against the latest final release's bundle, so a
version that understates the API change never goes out. A first release, or
a version past the latest one's breaking boundary (the major, or before 1.0
the minor), needs no comparison. A dry run only reports the bump the change
needs. Run `roc bump --old <latest bundle URL> platform/main.roc` to choose a
version before writing its notes.

To cut a release:

. Write `docs/releases/<version>.adoc`, opening with
  `= roc-native-macos <version>` and naming the platform as
  `{platform-url}`, and merge it. The pull request's dry run renders it.
. Run *Release* from the Actions tab on `main` with the version, or
  `gh workflow run release.yml --ref main -f version=<version>`.
. Approve the `release` environment's deployment when the tests pass.
. If publishing stops partway, follow roc-automation's "Recover an
  interrupted publication": delete a draft and re-run the publish job; a
  published release is never repaired.

No secret is needed: every job uses the workflow's own token. The settings
the workflows rely on are listed under <<repository-settings>>.

Every workflow step that runs repository code is one line calling a
Blueprint task, with the logic in `scripts/` and its decisions in
`scripts/src` with `expect`s; values from the run reach a script through its
environment, never its arguments' shell expansion. What stays inline is the
nightly's one-line resolution roc-automation prescribes, and the steps of the
jobs that hold write or attestation authority, which run no repository code:
exporting the attestations, the published digests and the dry run's
aggregate. The cross-compiling jobs are inline too: they show that an author
needs nothing but Roc and the release's files, with no checkout, Blueprint or
Xcode.

The scripts the workflow runs are tasks, so the build job's steps run the same
way locally (with the nightly as `roc`):

[source,sh]
----
blueprint run check
blueprint run bundle -- --prebuilt --output-dir build/release
blueprint run release -- tool 0.0.1-dryrun build/release
blueprint run release -- archive 0.0.1-dryrun build/release
blueprint run release -- test build/release
blueprint run release -- notes 0.0.1-dryrun build/release build/release-notes.md
----

[#repository-settings]
=== Repository settings

The workflows enforce nothing by themselves; these settings, from
roc-automation's "Repository settings" chapter, do:

* Actions: the default workflow token is read-only, and Actions may not
  create or approve pull requests.
* A ruleset on `main`: require a pull request, require the status checks
  `Check` and `Check on an Intel Mac` (`ci.yml`), `Release dry run`
  (`release.yml`) and `Build the manual`
  (`docs.yml`) on the current commit with the branch up to date, require
  signed commits, and give no bot a bypass. Merge commits stay allowed: the
  linker-input publisher binds its evidence to the exact commits of a pull
  request, which a squash would replace.
* A tag ruleset on all tags that restricts updates and deletions.
* Immutable releases.
* A `release` environment restricted by name to `main` ("Selected branches
  and tags"), with a required reviewer once there is more than one
  maintainer.
* Pages built from GitHub Actions, and a `github-pages` environment
  restricted by name to `main`.
* Private vulnerability reporting, as `SECURITY.md` describes.
* Dependabot's weekly `github-actions` updates (`.github/dependabot.yml`).

roc-automation's `check-settings` task reads them back with a maintainer's
own `gh` login and only ever makes `GET` requests. From a checkout of
roc-automation:

[source,sh]
----
blueprint run check-settings -- --platform lukewilliamboswell/roc-native-macos
----

Every failing line is printed with the settings page or `gh api` command that
fixes it. A real pull request with a failing check is still what shows that a
merge is blocked.

=== Nightly compatibility

`.github/workflows/nightly.yml` asks each day whether the latest final
release still works with the latest Roc nightly. It downloads that release's
bundle, `macos.roc` and examples archive, and runs `blueprint run release --
test` on them on `macos-15`: every archived example is built against the
published bundle and runs its specs, and an app is created, built
and tested with the release's `macos.roc`. A failure opens or comments on one
tracking issue, kept by roc-automation's `actions/nightly-report`, and the
next pass closes it. The fix is a patch release that works with the new
compiler; the archive is never changed. A manual run with `nightly-tag` or
`release-tag` reproduces a past pair and leaves the issue alone. Before the
first release it fails selection, since there is nothing to test.

[#styling]
== Styling

Apps style elements through props records in AppKit's own vocabulary; the
API is in xref:ui.adoc#ui-looks[the Ui reference] and the attribute grammar and
AppKit mapping in xref:architecture.adoc#looks[Looks]. Adding a look:

. a defaulted field on the props type in `Ui.roc` whose type is a tag union
  (or a number with a real native default), with a "platform decides" tag
  such as `Auto` or `Standard` rather than a magic zero;
. a word function outside the `Ui := [].{ … }` block, and an `expect` for
  its words;
. an `applyAttr` case in `host/Views.swift` that parses the word and calls
  `fatal` on anything else, independent of the order attributes arrive in
  (a template row applies them in dictionary order);
. any new AppKit symbol in `host/interfaces.json`, by documented ownership;
  watch for Swift type metadata (a stored `NSEdgeInsets` or `[CGFloat]`
  names CGFloat's descriptor in `libswiftCoreGraphics`, which the stubs do
  not link);
. a row in `docs/ui.adoc` and `docs/architecture.adoc`.

Check both appearances with `ROC_APPEARANCE=dark` and a screenshot
(`window`, then `screencapture -l<number> -o`).

[#findings]
[#findings]
== Constraints to build with

These hold for the compilers and the host as they are; each is a rule to
follow when changing the platform.

List capacity encoding:: In `capacity_or_alloc_ptr` a list stores
`capacity << 1`, and the low bit marks a seamless slice. A host that stores
the raw length makes every odd-length payload read as a slice with a bogus
allocation pointer. Build lists only with SwiftGlue's helpers.
Handles in host memory:: Roc frees a `Box(U64)` at its payload minus 8 with
alignment 8, where the glue's layout facts put it, so a box minted in a host
table (not from `roc_alloc`) is released through `roc_dealloc`, as the
browser host's blob heap is. A list of such boxes needs the 16-byte header
(element count, then refcount), which Roc reads when it releases a seamless
slice of the list; the 8-byte header of a byte list is wrong for it.
Single-field record builder:: `{ a: Engine.cell(…) }.Engine.Cells` with one
field is unimplemented in RC1-era compilers, but `roc build` compiles it to a
runtime error instead of failing. `roc test` reports it; give a store at
least two cells.
`watch` and `watch_latest`:: `watch` never cancels what it issued; a
start/stop effect such as an interval needs `watch_latest`.
Props records:: A nominal record of `??` defaulted fields as an argument
(`Ui.vstack({ align: Fill }, kids)`) takes every default for `{}` and for the
fields a literal omits, for every field type `Ui` uses, inside a `map` lambda
and through `Engine.const` too. An unannotated value such as
`card = { padding: All(4) }` is inferred as its own closed record and takes
no defaults: passing it where `Ui.BoxProps` is expected fails to type-check,
so themes are annotated (`card : Ui.BoxProps`).
A text literal is a constant signal:: `Signal` has `from_quote` and
`from_interpolation`, so `Ui.text("Hi", {})` and `Ui.text("${count} left", {})`
need no `Engine.const`, but a `Str` held in a name does.
Attributes arrive in any order:: A template row's views are made and then
given every attribute from a dictionary, so a host handler must not depend
on another attribute having been applied first. `title-display` is
reapplied after any title, bezel or size change for this reason.
No `Str` order:: `Str` has no ordering in RC1, so `Engine.sort_by` cannot
sort rows by a name; `contacts` sorts by key.
Erased calls can borrow their captures:: Every site is an erased closure
(the state crosses to the host in a `Box`), and an erased call reads its
captures borrowed when the call is in tail position or the result holds
exactly one function. A site's block is then shared, and rebuilding it
copies its child list: with 10,000 sites in one block, a 2.4 MB copy and
most of a 2.5 ms hover turn. roc-signals avoids both since 0.8.0-rc2
(`Core.call` keeps a site call out of tail position, and `Inst` has a
`Spare` variant; `patches/roc-compiler`, "Erased closures borrow their
captures"). Mount was quadratic, also the compiler's doing, until the same
release mounted each node kind in a function of its own.
Take a large value apart with `match`:: In optimized builds a record or
tuple taken apart by a destructuring statement (`{ rows, record } = table`,
`(root2, out, tx2) = call(..)`) or a parameter pattern (`|{ t }| t`) keeps
its refcounted parts shared until the function returns, so an update of one
copies it. `match table { { rows, record } => .. }` moves them. Every table
write copied the table's rows, and a `table_view` its columns, until
roc-signals 0.8.0-rc2 (`patches/roc-compiler`, "Destructuring leaves the
parts shared").
`Dict.update` can copy the dictionary:: In some programs a dictionary
grown with `Dict.update` is shared when it grows, so each update copies
it; `contains` and `insert` do not. Building a table with `Table.insert`
in a loop was quadratic for this reason (the table's change record) until
roc-signals 0.8.0-rc2; keep `Dict.update` off the engine's write paths
(`patches/roc-compiler`, "Dict.update copies a dictionary the loop
owns").
A bundle is fetched only over https, or http to localhost:: Roc rejects a
local `.tar.zst` path as a platform and an absolute platform path, and
accepts plain `http` only for `localhost`, `127.0.0.1` and `[::1]`. It
connects to `localhost` on the first loopback address it resolves to, `::1`
on macOS, so serve a bundle on `::` (`--bind ::`), which serves both.
The same inputs bundle to the same name:: `libhost.a` is byte-reproducible
(each object compiled to a fixed relative path under `build/host`, since
Swift hashes an object's output path into its `__swift_modhash`; every
path relative; `libtool -static -D` over the sorted objects with
`ZERO_AR_DATE=1`), so rebuilding the platform from the same commit names the
same bundle.
