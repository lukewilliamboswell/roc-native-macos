= roc-automation review
:toc: left
:toclevels: 2

This page reviews roc-native-macos against the
https://github.com/lukewilliamboswell/roc-automation[roc-automation] manual, at
roc-automation `6c796f2`. Each section says what the guidance requires, what
this repository does, and the decision:

* *adopt now*: done in the commit that added this page;
* *adopt later*: wanted, but blocked or out of scope for the spike; and
* *not applicable*: the guidance does not apply here.

The repository's shape decides what applies. It is a platform with one native
target (`arm64mac`). Its host is Swift, and it generates its own glue and macOS
linker stubs. It has no releases, so most of the release, nightly and SBOM
machinery has nothing to act on yet. roc-gui, which also generates macOS linker
interfaces, and roc-signals, the source of the engine, were the reference
adopters.

The guidance keeps implementation gaps in issues, not in documents
(roc-automation `AGENTS.md`). Once the follow-ups at the end are filed as
issues, delete this page.

== Repository layout and required files

Guidance::
`repository.adoc` "The layout" and "What is committed": `Blueprint.roc` and
`Blueprint.lock`, `platform/main.roc`, `examples/` on the working tree,
`scripts/*.roc` with modules in `scripts/src/`, and cases under `tests/`.
Build output, bundles and native binaries are not committed.
`documentation.adoc` "Keep the README short": `SECURITY.md` gives the private
reporting channel, and license and third-party notices stay in their required
places. `settings.adoc` "Dependencies": a weekly `github-actions` Dependabot
entry.

This repository::
The layout already matched for `platform/`, `examples/` and the ignored build
outputs (`.gitignore`). It had no Blueprint files, `tests/`, `SECURITY.md`,
third-party notice or Dependabot configuration. `platform/Url.roc`'s header
says "see THIRD_PARTY_LICENSES.md", which did not exist.

Action (adopt now)::
Added `Blueprint.roc`, `Blueprint.lock`, `scripts/check_all.roc`,
`scripts/src/Repo.roc`, `tests/`, `SECURITY.md`, `THIRD_PARTY_LICENSES.md` and
`.github/dependabot.yml`. `.gitignore` now lists `.blueprint/` and
`.claude/worktrees/`, as roc-gui's does. `THIRD_PARTY_LICENSES.md` covers the
engine copies, `Url.roc`'s basic-webserver origin and WPT-informed tests, the
fetched packages, and the system libraries and generated stubs, following
roc-signals and roc-gui.

== AGENTS.md

Guidance::
roc-automation, roc-gui and roc-signals each keep an `AGENTS.md` with the
repository's boundaries.

This repository::
None. Its real rules lived in the README and in people's heads.

Action (adopt now)::
Added `AGENTS.md`. It covers the verbatim engine modules and how to take a
newer engine, and the ban on Apple SDK material in linker inputs. It also
covers Roc's main-thread-only entry points, the glue and the list
`capacity << 1` encoding, `() ->` for zero-argument functions, the RC1-era
single-field record builder that builds but fails at run time, and
`watch_latest`.

== Blueprint environment and pinned tooling

Guidance::
`environment.adoc` "Declare the environment" and "Use the environment in CI":
every tool a script calls is declared, `Blueprint.lock` pins fetched bytes,
`RocPackages` lists every bundle the scripts use, and CI calls named tasks,
never script paths. `adopting.adoc` step 1.

This repository::
None. `scripts/build.sh` assumed the RC1 compiler at a fixed home-directory
path, with `swiftc` and `python3` from the machine.

Action (adopt now)::
`Blueprint.roc` declares one `dev` environment for `aarch64-darwin`. It
fetches `roc-stable` with its digest locked, prepares basic-cli 0.28.1 and
roc-lang/http 1.0.0 for the scripts, and expects `roc`, `bash`, `env`,
`swiftc`, `python3`, `shasum` and `git` from the machine. The tasks are
`check`, `build` (`scripts/build.sh` with `ROC=roc`), `test`, `examples` and
`tooling-version`. Xcode's `swiftc` cannot be fetched, so it stays an `Expect`,
like roc-signals' `google-chrome`. The Swift version therefore follows the
runner image: CI prints `swiftc --version`, and this Mac has Swift 6.2.4.

== Roc compiler policy

Guidance::
`overview.adoc` "Three compilers, three jobs": the package compiler is the
latest nightly and is never pinned. `roc-stable` runs the scripts.
`repository.adoc` "Where a compiler pin belongs" and "Keep the script pins in
step": a `roc:` header field appears only under `scripts/`, names
`roc-stable`'s tag, and the check script enforces both.

This repository::
The README and `scripts/build.sh` named the 0.1.0 RC1 compiler. The guidance
has no place for a release candidate as the package compiler, and
`roc-lang/setup-roc` installs only nightlies. RC1 is roc-lang/roc `15177e9`,
two commits after `09f4dc3`, the source of `nightly-2026-11-21-09f4dc3`. The
two commits change only Windows debug sections. No file carried a `roc:` pin.

Action (adopt now)::
The platform and the examples float on `roc`. They were built, unit-tested and
run with both RC1 and `nightly-2026-11-20-3b29392`, and they pass on both.
`check`'s `pins` stage fails on a `roc:` field outside `scripts/`, on a script
that does not pin `roc-stable`'s tag, and on `.roc-version` or
`.github/roc-nightly.json`. `scripts/build.sh` keeps its RC1 default, so its
interface is unchanged; the Blueprint tasks pass `ROC=roc`. A contributor can
keep RC1 installed as `roc`. Pinning RC1 against the guidance was rejected.
The model already expects to settle on Roc 0.1 once it is released, and RC1
is effectively the newest nightly today.

== Product automation as Roc scripts

Guidance::
`repository.adoc` "Write product-specific automation as Roc scripts":
orchestration scripts are Roc, with the `roc-stable` shebang and pin.
`adopting.adoc` "Acceptance": no Python, bash or PowerShell automation. Small
platform adapters may use the runtime their documented contract requires.

This repository::
`scripts/build.sh` (bash) builds the glue, host, stubs and examples.
`scripts/build_macos_stubs.py` (Python) generates the TAPI stubs, mirroring
roc-gui's `scripts/build_macos_stubs.py`. roc-gui itself keeps that generator,
and most of its producers, in Python.

Action::
*Adopt now* for new automation: the check driver is a Roc script, with its
pure decisions and their `expect` tests in `scripts/src/Repo.roc`.
*Adopt later* for the two existing scripts. Concurrent feature branches may edit
`scripts/build.sh`, so replacing it now would conflict with them; port
it to `scripts/build_platform.roc`, as roc-signals did, once they merge. The
stub generator moves with the linker-input producer (see
<<linker-inputs>>). roc-automation prescribes a Roc script, and roc-gui's
Python is not a precedent for a new one.

== Formatting, check and test gates

Guidance::
`testing.adoc` "What runs on every pull request": `roc fmt --check` over the
Roc sources, `roc-stable fmt --check` over the scripts, `roc test` on the
platform root, every example run against recorded cases, and the scripts'
`expect` tests, all in one `check` task. "Skip a broken case, visibly" and
"Report progress and results" cover how skips and results print.
`examples.adoc` "Record expected output".

This repository::
`roc test examples/todos/main.roc` was the only automated check. The engine
modules, `platform/Ui.roc` and the scripts pass `roc fmt --check` with RC1 and
with the nightly. `platform/main.roc`, `glue/SwiftGlue.roc` and the three
examples do not.

Action (adopt now, partly)::
`blueprint run check` runs these stages, in this order:
+
--
. `pins`: the compiler pins above.
. `engine`: the 13 engine modules match `tests/engine-modules.sha256`, which
  was checked against roc-signals `a13ff70e`. This control is particular to
  this repository: it keeps the verbatim-copy rule from depending on review
  alone.
. `fmt`: `roc fmt --check` and `roc-stable fmt --check`. The five unformatted
  files are skipped by prefix in `Repo.fmt_skips`, and every run prints each
  skip with its reason. They were not reformatted because the open feature
  branches edit them, and a formatting commit would conflict with each one.
  The engine modules are checked, not reformatted. If a future formatter
  disagrees with roc-signals' copies, re-copy them from roc-signals.
. `scripts`: `roc-stable test scripts/check_all.roc`.
. `build`: `scripts/build.sh` with the `roc` on PATH.
. `test`: `roc test` on `platform/main.roc` (294 engine tests) and on every
  example.
. `examples`: every case in `tests/examples/<example>/<case>.script`, run as
  `ROC_SCRIPT` against the built app with a 60-second deadline. The case must
  exit 0 and print exactly `<case>.expected`, which holds the `dump` trees.
  `-- --update` records new output, and an example with no case fails. The
  stopwatch cases avoid wall-clock readouts: one checks the initial state, and
  one starts, laps, stops and resets.
--
+
Results print as `[i/n] name .... PASS 1_204ms` lines with a summary, as
`testing.adoc` asks; colour is not implemented. A deliberately wrong
`.expected` file was confirmed to fail the stage with a diff.

== Continuous integration

Guidance::
`workflows.adoc` "The three workflows" and "Continuous integration": top-level
`permissions: {}`, full-SHA `uses:`, `persist-credentials: false`, no write
access for jobs that run repository code, the nightly resolved once and passed
as `nightly-tag`, and each job calls a Blueprint task. `actions.adoc`
"`actions/setup-blueprint`" and "Install the nightly compiler".
`platforms.adoc` "The runner jobs": `macos-15` for `arm64mac`.

This repository::
No workflows.

Action (adopt now)::
`.github/workflows/ci.yml` resolves the nightly on `ubuntu-24.04`. One
`macos-15` job, `Check`, installs Blueprint with
`actions/setup-blueprint@6c796f2` and the nightly with
`roc-lang/setup-roc@dd81390` (`version: nightly`), the revision roc-signals
uses. It runs `blueprint check`, then `blueprint run check`. With one target
and one job there is no aggregate job: `Check` is the required status check.
`actionlint` passes. Blueprint 0.13.0's recorded `aarch64-darwin` digest
matches the local binary the steps ran with.
+
The workflow has not run on GitHub yet. Two parts are untested there: AppKit
apps on a hosted runner's GUI session, and the runner image's Swift version.
`setup-roc` on `main` has no `download-method: asset-api`, so the verified
download `actions.adoc` asks for is a follow-up. It is on a roc-lang/setup-roc
branch (`30af91a`), which roc-automation's own workflows use.

== Host bindings

Guidance::
`platforms.adoc` "Host bindings": the generated bindings are committed, and
the host build reads them and never runs `roc glue`. A `ci.yml` job
regenerates them with the latest nightly and fails on `git diff`.
`adopting.adoc` acceptance: a deliberate edit to the committed bindings fails
`ci.yml`.

This repository::
`scripts/build.sh` runs `roc glue glue/SwiftGlue.roc` on every build, and
`host/roc_swift_abi.h` and `host/RocGlue.swift` are ignored by git. The glue
specification is the repository's own, `glue/SwiftGlue.roc`, so the check
needs no nightly source archive. roc-gui downloads one for its Rust glue.

Action (adopt later)::
Commit the two generated files, and have `scripts/build.sh` stop running
`roc glue`. Add a `bindings` stage or job that runs `roc glue` into a
temporary directory and compares the result. This waits because open
branches change `glue/SwiftGlue.roc` and `platform/main.roc`, and committed
generated files would conflict on every rebase.

== Native build inputs and linker-input releases

Guidance::
`platforms.adoc` "Native build inputs" and "Separate the artifacts by what can
invalidate them": macOS `.tbd` stubs are external linker inputs. They have
their own producer and an immutable release with a build-provenance
attestation, licenses and an SBOM, and consumers select them through a content
lock. The host gets its own fingerprinted, cached job. `linker-input-releases.adoc`
specifies `actions/publish-build-inputs`. roc-gui does this with
`link-inputs.lock.json`, `dependencies/macos-interfaces/` (catalog and
`PROVENANCE.md`), `link-inputs.yml` and `publish-link-inputs.yml`.

This repository::
The stubs are generated from `host/interfaces.json` during every build. No
SDK file is read, which is the property roc-gui's provenance statement
records. Nothing is released or locked, and the catalog's evidence is per
library, not per symbol.

Action (adopt later)::
Move the catalog and generator into a producer, for example
`dependencies/macos-interfaces/`, with a `PROVENANCE.md`. Publish the stubs as
a linker-input release through `actions/publish-build-inputs`, and consume
them through a committed lock that records digest, size and inventory. Add a
fingerprinted host job. This needs a `link-inputs` release environment, attestation
permissions and a maintainer-dispatched publisher, none of which a spike
without releases can exercise. Tightening the catalog to per-symbol evidence
is already listed in xref:architecture.adoc#linker-inputs[Architecture].

== Releases, examples archive and nightly compatibility

Guidance::
`workflows.adoc` "A platform's release workflow", `examples.adoc` "The
examples archive", `nightly-compatibility.adoc`, and `actions.adoc`
"`release-package`" and "`actions/publish-release`".

This repository::
No releases. The examples already name the platform by relative path
(`../../platform/main.roc`), and no example pins a compiler, so they can be
archived unchanged.

Action (adopt now, partly)::
`blueprint run bundle` (`scripts/bundle.roc`) is the repository's own bundle
command, as `actions.adoc` "`release-package` platform" expects. It builds the
platform's native inputs, stages the tracked `platform/*.roc` modules,
`libhost.a`, the generated `macos-sysroot` stubs and the licence notices, and
runs `roc bundle` into `build/platform/`, which then holds exactly one
`<hash>.tar.zst`. `--test` serves that directory on localhost and builds and
runs `examples/counter` against it with an empty package cache, as a first
user would; `check` runs it as its `bundle` stage.
+
*Adopt later*: when the platform is first released, add a `release.yml`
that builds the bundle with this task, with the host and the locked stubs. The workflow uses
`release-package build --platform-bundle` to write the examples archive, tests
those bytes on `macos-15` and publishes through `actions/publish-release`.
Then add `nightly.yml` on the shared compatibility runner. Both need
`tests/spec.json`, which needs the host to take its script from standard input
or an argument rather than `ROC_SCRIPT` (see the follow-ups).

== Repository settings

Guidance::
`settings.adoc`: read-only default token, required status checks, tag
protection, `release` and `github-pages` environments restricted to the
default branch, and confirmation with roc-automation's `check-settings` task.

Action (adopt later)::
A maintainer applies these after `ci.yml` first passes: make `Check` the

== Repository policy utility

Guidance::
`policy.adoc`: `roc-policy`, a released utility that checks compiler pins,
imports, spelling and documentation from `repository_policy` in
`Blueprint.roc`. `repository.adoc` "Use shared utilities through Blueprint
tasks".

Action (adopt later)::
The `pins` stage is a bespoke check, about 40 lines, modelled on roc-signals'.

== Documentation

Guidance::
`documentation.adoc`: a short README that links into an AsciiDoc manual under
`docs/`, built with roc-docs.

This repository::
The README was the only documentation, and it held design notes and findings.

Action (adopt now, partly)::
The README is the front door for app authors: the pitch, a screenshot, a
quick start with a complete example, a short tour, the examples and the
licence. `docs/index.adoc` is a `:doctype: book` that includes one chapter
per file: `ui.adoc` (the `Ui` reference, for app authors),
`architecture.adoc`, `contributing.adoc` and this page. `docs/styling.md`
stays Markdown: it is a design proposal, not a chapter, and is replaced by
the implementation. *Adopt later*: build the manual with roc-docs in CI.

== Not applicable

* *Fuzzing, benchmarks and allocation checks* (`testing.adoc`): the
  repository has none. The engine's fuzz targets live in roc-signals.
* *A cross-compiling builder and a runner matrix* (`platforms.adoc` "Cross-compile
  once, run on every target"): the only target is `arm64mac`, built and run
  on one runner. The README says that `x64mac` is unsupported.
* *Kai* (`kai.adoc`): Blueprint is the environment.
