= Build an app

Create, test and share a native Mac app with `macos.roc`, the tool included in
each release. For control signatures, props and events, see
xref:ui.adoc#builders[the Ui reference].

[#get-started]
== Get started

To run the app, use an Apple silicon or Intel Mac with macOS 15 or later.
Install Roc as `roc` on your PATH. Use the compiler named by the
https://github.com/lukewilliamboswell/roc-native-macos/releases/latest[release]
or a compatible https://github.com/roc-lang/nightlies/releases[nightly].
You can build the app on macOS, Linux or Windows using the prebuilt host
and linker inputs in the release.

Copy the `roc run … init my-app` command from the release notes. Roc fetches
the installer and writes the starter and its local `macos.roc` launcher into
`my-app`. If the release notes omit that command, download `macos.roc`
from the release page and run `roc macos.roc init my-app` from the
download directory.

Start the app in development mode from the project directory.

[source,sh]
----
cd my-app
roc macos.roc dev
----

The music player opens with a song in its queue. Press Play to see the
visualizer and Command-L to show the timed lyrics. Quit with Command-Q to
return to the terminal.

With the runnable installer, pass `--simple` after `init` to start with
a counter in one source file.

Roc watches your source files and rebuilds when you save. Press Command-R
in the app to load the changes. See xref:apps.adoc#hot-reloading[Hot reloading].

[#layout]
=== How an app is laid out

----
my-app/
  src/main.roc       the program: its store, window and workers
  src/Store.roc      shared state, and the decisions that change it
  src/Player.roc     the window, composed from the store and the panels
  src/Words.roc      the lyrics over the picture, and reading lyric files
  src/Panels.roc     the queue and EQ panels
  src/Editor.roc     the preset editor panel
  src/Widgets.roc    reusable widgets, which know nothing of the store
  src/Export.roc     a worker task, and the site that asks for its jobs
  src/Media.roc      the audio session: commands out, events in
  src/Visual.roc     the drawing surface: a scene in, a picture out
  logic/             lyrics, the queue, presets and scenes: pure Roc, no platform
  assets/            its icon, the default song and its lyrics, and their credits
  tests/specs/       specs of the app: what its controls do, run by `test`
  tests/fixtures/    the songs, lyrics and preset files the specs use
  tests/fuzz/main.roc  roc-fuzz targets for the logic package, run by `fuzz`
  macos.json         the app's name, bundle identifier and version
----

`init --simple` writes the same layout with only `src/main.roc` and
`tests/specs/`, beside the same `macos.json`, `macos.roc`, `.gitignore` and
workflow; add `assets/`, `logic/` and `tests/fuzz/` as the app needs them.

The starter's module comments explain where to make changes and link to
the relevant manual sections. The project also includes `macos.roc`,
`.gitignore` and `.github/workflows/release.yml`. See
xref:apps.adoc#ship-your-app[Ship your app] for the release workflow.

[#starter-seams]
==== Where the starter meets the platform

`src/Media.roc` sends commands to xref:ui.adoc#audio[the Audio session] and
receives playback events and status. The playback position determines
which lyric line to show.

`src/Visual.roc` renders a preset's scene from `logic/Scene.roc` on a
display-paced xref:ui.adoc#drawing[drawing surface]. The surface reads
audio measurements every frame without calling Roc. A `Ui.overlay` draws
the lyrics separately from the visualizer's trail. Presets can include
xref:ui.adoc#shaders[Metal shaders]. Their layers and feedback provide
the Core Graphics fallback shown as “Simple visuals”. Specs exercise
playback and drawing with manual clocks.

The root module, `src/main.roc`, names the platform by its release URL and
the logic package by its path. This header shows the layout with placeholders
for the release version and bundle hash.

[source,roc]
----
app [main] {
	logic: "../logic/main.roc",
	pf: platform "https://github.com/lukewilliamboswell/roc-native-macos/releases/download/<version>/<hash>.tar.zst",
}
----

`logic/main.roc` is a package header, `package [Lyrics, Preset, Queue, ...] {}`,
so the app imports `logic.Lyrics`; the logic cannot import the platform, which keeps
it testable independently of the app. Each release's notes give the platform
URL to use when xref:apps.adoc#without-the-tool[building without the tool].

[#work-on-the-starter]
==== Work on the starter

A view reads state through signals. An event handler returns writes, and
the engine applies them and wakes the sites that read the changed state.

* Put shared state and the pure decisions that update it in
  `src/Store.roc`. To test a decision, apply its writes and inspect the
  result with `Store.store.after(writes).read(cell)`.
* Use `Engine.state(initial, |state| ...)` for state local to a widget,
  such as whether a section is folded. Use `signal.map(...)` for a value
  computed from state, or `Engine.derive` to share the computation.
* Keep effect requests beside the code that handles their answers.
  `Store.send` posts audio commands to the outbox and `Media.session`
  sends them. Use one outbox post per turn.
* Put rules that need no window in `logic/`. Run their `expect` tests
  and xref:apps.adoc#fuzz-the-logic[fuzz targets] independently of the UI.

To add a layer kind, start with `logic/Preset.roc` and draw it in
`logic/Scene.roc`. The editor reads the choices from `Preset.kinds` and
`Preset.properties`. To add a built-in preset, register it in
`Library.builtins`. The starter includes Orb Garden as its default, 15
visualization presets in all, and a separate Sync Test preset.

Try a shader in the editor's Warp or Composite area. The surface reports
the line of a compile error and keeps the last working shader for that
stage. See xref:ui.adoc#shaders[Shaders] for the function signatures, inputs
and parameter limits. To adjust picture timing for your audio output, use
the EQ panel's Picture sync control with Sync Test. Use a positive offset
when the ring flashes before the click.

The default song, _Polymorphic Defunctionalization Through Lambda Set
Specialization_ by Luke Boswell, is licensed under CC BY 4.0. Keep
`assets/CREDITS.md` with the song. For the steps to remove it and start with
an empty queue, see the comment on `Store.default` in `src/Store.roc`.

[#the-tool]
== The tool's commands

Run `init` from the directory where you want to create a project.
Use the installer URL from the release notes, or run a local `macos.roc`
from the directory containing it. For an existing app, run commands from
the directory containing its `src/main.roc` and `macos.json`.

[cols="1,2",options="header"]
|===
| Command | What it does

| `roc macos.roc init [DIR]` | create an app in `DIR`, or in this directory: the starter, a music player; it checks for conflicts before writing
| `roc macos.roc init --simple [DIR]` | create the counter instead, one `src/main.roc` and its specs, with the same `macos.json`, `.gitignore` and release workflow
| `roc macos.roc build` | build `<name>.app`, universal, on any system; `--target arm64mac` or `--target x64mac` builds it for that Mac alone
| `roc macos.roc dev` | run the app with Roc's file watcher on a Mac and press Command-R to remount it after saving. The bundle metadata and icon apply when you build or run the `.app` (xref:apps.adoc#hot-reloading[Hot reloading])
| `roc macos.roc run` | build the app and start it, on a Mac; it takes `--target` as `build` does
| `roc macos.roc test` | run the app's `expect` tests, then run its specs on a Mac. `--update` records dumps and tightens allocation bounds. `--metrics` reports measurements. `--check` parses specs and demos on any system
| `roc macos.roc fuzz` | build the app's roc-fuzz targets, `tests/fuzz/main.roc`, and run each for 10 seconds, on an Apple silicon Mac or Linux x64 (roc-fuzz has no Intel Mac target); `--check` runs only their declared examples, `--time SECONDS` longer, and target names only those (xref:apps.adoc#fuzz-the-logic[Fuzz the logic])
| `roc macos.roc package` | build and zip the app on any system as `dist/<name>-<version>.zip`. Use `--sign` for Developer ID signing, `--notarize` for signing and notarization, or `--target` for one slice in `dist/<name>-<version>-<target>.zip` (see xref:apps.adoc#ship-your-app[Ship your app])
| `roc macos.roc ci package`, `ci release` | what the release workflow runs: package the app as the secrets allow, and attach the zip to the pushed tag's GitHub release (see xref:apps.adoc#automate[Let GitHub release it])
|===

`<name>` is the app's directory. `roc macos.roc COMMAND --help` describes a
command, and every failure is explained in a sentence.

`build` runs `roc build src/main.roc --target=arm64mac` and `--target=x64mac`,
which write the program for Apple silicon and for Intel Macs, joins the two
into one universal program, `.macos/<name>`, with no Apple tool, and puts it
in a minimal `.app` with its xref:apps.adoc#assets[assets and icon] and
xref:apps.adoc#metadata[metadata]. The `name` metadata field sets the bundle
file name. Each Mac runs its own slice natively.

`build`, `run`, `package` and `ci package` accept `--target arm64mac` for a
smaller Apple silicon app or `--target x64mac` for an Intel app. Use the
matching native build on each Mac. `test` builds a single slice for the Mac
where it runs. `dev` uses Roc's run mode on that Mac.

The tool uses `roc build --opt=size` to reduce compile time and memory for
apps with many store cells and handlers, such as the starter.

[#metadata]
=== The app's metadata

`macos.json`, at the top of the app's directory, says what the app's `Info.plist` holds. It
is one JSON object of text fields, every one optional, and `init` writes a
starter:

[source,json]
----
{
  "name": "Counter",
  "id": "com.example.counter",
  "version": "1.2.0",
  "build": "7",
  "copyright": "© 2026 Jane Doe",
  "category": "public.app-category.utilities",
  "minimum_macos": "26.0"
}
----

[cols="1,1,3",options="header"]
|===
| Field and flag | `Info.plist` key | What it is

| `name`, `--name TEXT` | `CFBundleName`, `CFBundleDisplayName` | the name in the menu bar, and the `.app`'s file name, which Finder and the Dock show (a `/` or `:` becomes `-`); by default `<name>`
| `id`, `--id ID` | `CFBundleIdentifier` | the bundle identifier, two or more dot-separated parts of letters, digits and hyphens; by default `com.example.<name>`. It also names the app's saved settings (`UserDefaults`), so keep it once people use the app
| `version`, `--version 1.2.0` | `CFBundleShortVersionString` | one to three whole numbers separated by dots, with no `v`, and optionally a pre-release suffix, as in `1.2.0-beta.1`; by default 0.1. It names the zip `package` writes, suffix and all, while `Info.plist` has its numbers alone, `1.2.0`, as macOS requires
| `build`, `--build 7` | `CFBundleVersion` | the build number, one to three whole numbers with no suffix; by default the version's numbers. Set it to tell builds of one version apart, such as a beta from the release that follows it
| `copyright`, `--copyright TEXT` | `NSHumanReadableCopyright` | shown in the app's About panel
| `category`, `--category CATEGORY` | `LSApplicationCategoryType` | an App Store category, `public.app-category.` and its name, such as `utilities` or `developer-tools`
| `minimum_macos`, `--minimum-macos 26.0` | `LSMinimumSystemVersion` | the oldest macOS the app opens on; by default 15.0, the oldest the platform runs on, and never earlier
|===

`build`, `run` and `package` take each field as a flag, which overrides the
file, so a release can set its version with `--version` and leave the rest
in `macos.json`. A field the tool does not know, a value that is not text,
or a version such as `v1.2` is refused with the line or flag it came from.
The file is named for the tool that reads it, as `macos.roc` is, so it does
not clash with another tool's `app.json`.

[#write-an-app]
== Write an app

Programs and state:: `Engine.program(|| view)` is an app with no store;
local state comes from `Engine.state(initial, |s| ...)`, as in the counter
and in the starter's folding sections and confirm buttons (`src/Widgets.roc`).
An app with shared state declares a store of cells and builds its view from
their signals:
+
[source,roc]
----
main : Engine.Program(_)
main = Engine.program_store({}, |_boot| store, |_boot| view())

store = Engine.store(
	Stopwatch,
	{
		running: Engine.cell(Bool.False),
		elapsed_ms: Engine.cell(0.I64),
	}.Engine.Cells,
)

cells = store.cells()
----
+
A store needs at least two cells: a single-field record builder builds but
fails at run time with current compilers (`roc test` reports it).

The view:: Every builder in `Ui` is a native control: stacks, forms, scroll
areas, lists backed by `NSTableView`, labels, buttons, text fields,
checkboxes, sliders, pop-up menus, segmented controls and tabs, SF Symbols,
progress bars, keyboard shortcuts, file pickers and drop zones, and `box`
surfaces. Each takes its subject first and a props record of defaulted fields
beside it (containers take their children last); name only what differs:
`Ui.text("Saved", { style: Caption1, color: SecondaryLabel })`,
`Ui.vstack({ spacing: 12, align: Fill }, kids)`. Looks are AppKit's own: text
styles, semantic colours that follow dark mode, control sizes, bezels and SF
Symbols. State is a signal and looks are values: a literal text is a constant
and `"${count} left"` follows `count`; when a look must follow state too, the
`_s` form takes the props as a signal,
`Ui.text_s(total, over.map(|o| if (o) { color: Red } else {}))`. An app
shares a look as a plain annotated value, `theme : Theme`, not a stylesheet.

Events:: Handlers are props fields that return writes to state:
`Ui.button("Reset", { on_press: Engine.handle(|_| [cells.elapsed_ms.set(0)]) })`.
A text field's `on_input` receives the text, a checkbox's `on_change` its new
state.

Effects:: HTTP requests, timers and intervals, file reads and digests are
asks that a watch site issues when a signal changes, and whose answers come
back as writes. `Engine.watch_latest` cancels what it issued when the signal
changes again:
+
[source,roc]
----
Engine.watch_latest(
	cells.request.signal(),
	|r| if r.active [Engine.http({ url: r.url, timeout: Ms(2000), cache: NoStore })] else [],
	Engine.react(answered),
)
----

Files and storage:: Files reach the app as handles, never bytes:
`Ui.file_button` and `Ui.drop_zone` deliver `File`s, which `sha256`,
`read_utf8`, `read_bytes` and `File.save` act on. Local storage is
`UserDefaults`: declare the keys in
`Engine.program_store({ storage_keys: ["todos"] }, ...)`, read them at boot
with `Engine.boot_storage` and write them with
`Engine.command(StorageSet(key, text))`.

Images:: `Ui.image("star.fill", {})` draws an SF Symbol;
`Ui.asset_image("logo.png", { width: Fixed(64), label: "Logo" })` draws an
image the app ships in `assets/` (xref:apps.adoc#assets[Assets and the icon]).

xref:ui.adoc#builders[The Ui reference] lists every builder with its
signature, what it draws and the events it sends. The engine itself
(`Engine`: signals, stores, tables, watches) is documented in
https://github.com/lukewilliamboswell/roc-signals[roc-signals].

Small screens:: The window never grows past its screen, and what does not
fit scrolls with the whole window (xref:ui.adoc#the-window[The window]),
which is a last resort. Give anything tall a scroll area of its own
(`Ui.scroll`), so the controls around it stay in sight: the starter wraps
each panel in one (`Player.scrolled`), as its preset list is, and its
`small-screen` spec runs it on a 760 by 560 screen with
`(screen-size W H)`.

[#gotchas]
=== Things to know

* A store needs at least two cells: a single-field record builder,
  `{ a: Engine.cell(0) }.Engine.Cells`, builds but fails at run time.
  `roc test` reports it.
* Post to an outbox at most once a turn: a decision that sends several
  commands sends one list.
* `Engine.watch` and `Engine.watch_changes` never cancel what they asked
  for. Anything that must stop or restart when its value changes (an
  interval, a timer, a file read a newer one supersedes) belongs under
  `Engine.watch_latest`.
* A builder's text is a signal. A literal works as one; a `Str` value needs
  `Engine.const(value)`, and state needs `.signal()` or `.map`. A signal
  from outside a local state or a row enters it with `.lift()`.
* A dropdown's `choices` and a slider's `range` are fixed when it is built:
  a list that changes is an `Engine.each` of buttons.
* An `Engine.each` row's template builds a single element: a widget with
  local state, an `Engine.when` or a `switch` is not one, so wrap it in a
  stack.
* A helper whose parameter is a signal used at two types needs a type
  annotation; without one the compiler reports two incompatible `map`
  methods.
* Roc does not allow shadowing, and a type module's own functions are in
  scope throughout it, so a local cannot reuse one's name. A type module
  cannot hold a type of its own name (`Preset.Preset`), nor be named after
  a builtin. `app` and `where` are keywords. A function with no arguments
  is `() -> T` in annotations and `|| ...` in definitions.
* A local package such as `logic/` cannot import the platform: code that
  needs `pf.` belongs in `src/`.
* Hot reloading keeps the state the old code built until Command-R: after
  changing a cell's or a state's type, press Command-R before anything else.

[#assets]
== Assets and the icon

Everything an app ships lives in its directory. Put images and other files
in an `assets/` directory at its top, beside `src/`:

----
my-app/
  src/main.roc
  assets/
    icon.png        the app's icon
    logo.png
    icons/star.pdf
  tests/
----

Images:: `Ui.asset_image(name, props)` draws `assets/<name>`: a PNG, JPEG,
PDF (drawn as vectors at any size) or any other file AppKit reads as an
image. The name may name a subdirectory (`"icons/star.pdf"`), but never leave
`assets/`. The name is a signal, so `shown.signal()` switches the image. An
image's natural size is its size in points (a PNG's pixels, unless it records
a resolution); bind one side, `{ width: Fixed(64) }`, and the other follows
its aspect ratio; bind both and `scaling` (`Fit`, `Fill`, `Stretch` or
`Original`) fits it to the frame. Give it a `label` for VoiceOver unless it is
decorative. The `about` example shows a PNG and a PDF.

Missing assets:: An asset is read when
it is first shown and kept for the rest of the run. A name that is not in
`assets/`, or a file that is not an image, stops the app with an alert (and a
line on standard error) naming the asset and the directory it looked in,
never a blank view.

The icon:: `assets/icon.png` becomes the app's icon: a square PNG, best 1024 by
1024 pixels with the transparent margin macOS icons have (16, 32, 64, 128,
256 and 512 pixels also work). `build` wraps it in `AppIcon.icns` itself, so
no Apple tool is needed and it works from Linux and Windows; macOS scales the
one image for the sizes it shows. For hand-tuned small sizes, make an
`assets/icon.icns` with Apple's `iconutil` and use it instead (not both). The
icon shows in the Finder and the Dock once the `.app` runs; a running bare
program (`.macos/<name>`) has the generic icon.

Data files:: A file the app reads as data, such as a word list or a JSON
table, is best compiled in: `import "data/words.txt" as words : Str` (or
`: List(U8)`) at the top of a module makes it a value, with nothing to find
at run time. The path is relative to the module, so such files can live
anywhere in the app's directory.

Where they go:: `build` copies `assets/` into
`<name>.app/Contents/Resources/assets/`, and beside the program it tests,
`.macos/assets/`. The program looks in `ROC_ASSETS` when that is set, then in
the `.app` it is in, then in `assets/` beside itself, and a bare program last
in `assets/` of the directory it was started in, which is how
`roc src/main.roc`, run from the app's directory, finds them. So copy the whole `.app` to share it; a bare program moved away
from its assets needs `ROC_ASSETS`.
The assets are plain files in the bundle: the program's ad hoc signature does
not cover them, as it does not cover `Info.plist`.

[#hot-reloading]
== Hot reloading

On a Mac, `roc macos.roc dev`, run from the app's directory,
starts the app for hot reloading. It runs `roc src/main.roc` (you can run
that yourself, and `roc run src/main.roc` is the same), which compiles the app with Roc's fast
development backend and starts it straight from the compiler, with no
`.app`. Roc also watches the root module and every module and local package
it imports.
When you save a change that compiles, Roc rebuilds the app in the background
and loads the new code into the running program; a change that does not
compile prints its errors and leaves the running code alone. Quit the app to
return to the terminal.

[source,sh]
----
cd my-app
roc macos.roc dev
----

`dev` runs it from the build directory, `.macos/`, because Roc's watcher
makes a `.zig-cache/` directory in the directory it runs in, for the list of
files it watches (https://github.com/roc-lang/roc/issues/13420[roc-lang/roc#13420]); run yourself, `roc src/main.roc` makes it where you run it,
and the `.gitignore` `init` writes leaves it out. The bare program finds its
images in `assets/` of the app's directory, as the `.app` does: `dev` sets
`ROC_ASSETS` to it, unless you have. `macos.json` and the icon belong to the
`.app`, which `dev` does not make, so they do not apply and `dev` takes none
of the metadata flags; `roc macos.roc run` shows the app as people will see
it.

What reloads:: Roc swaps the code in at the next call into the app, but this
platform's window keeps the views and the state it mounted with the old
code, so the old code still answers its buttons. Press Command-R (*Reload*
in the app menu) to see the change: it drops the window's engine and mounts
a fresh one, which runs the newest code. If Command-R comes before Roc has
finished the rebuild, which the terminal reports as `hot reload generation
N accepted by host`, press it again.
What survives a reload:: Local and session storage, and the window. The
state, the view tree, and every timer, request, file job and worker job in
flight start again, as when a browser reloads a page.
Limits:: Change the state's types (an `Engine.state`'s value, a store's
cells) only with Command-R right after saving: until then the new code is
handed the state the old code built. A change to the platform's interface
asks you to restart `roc macos.roc dev`. A reload keeps the old state's memory
rather than release it with code that may describe it differently, which is
harmless while you develop. *Reload* appears only in a bare program, such as
the one `roc src/main.roc` runs, never in an `.app`.
Compilers:: Roc 0.1.0 RC1 and current nightlies. `roc --opt=interpreter
src/main.roc` runs the app too, but only the default development backend hot
reloads.

[#test-an-app]
== Test an app

`roc test src/main.roc` runs the app's `expect` tests: those of every
module of the app, and of the packages its header names by path, such as
`logic/`. It works on any system, and also reports the single-field record
builder (`{ a: Engine.cell(…) }.Engine.Cells`), which builds but fails at run
time. Keep decisions (functions that return a store's writes) and logic
pure, and test them there: `Store.store.after(writes).read(cell)` is the
state after the writes, with no window.

`roc macos.roc test` runs those `expect` tests, then the app's specs: each
`tests/specs/<name>.scm` holds one behaviour spec, steps a person could take
and what the app should then show. Files a spec opens or drops live in
`tests/fixtures/`, and its steps name them relative to the app's directory,
as `(files "tests/fixtures/song.wav")`. A spec written `(demo "name" …)` in
place of `(test "name" …)` is a demo: the same grammar, usually with
`(live-effects)` and real `wait`s, to show the app or record it. `test
--check` parses a demo, and `test` never runs one, since its timing is
real.

A spec is one `(test "name" …)` form: an optional `(setup …)`, then
`(steps …)` with at least one step, run in order from a fresh window. `;`
starts a comment. Strings know the escapes `\n`, `\t`, `\"` and `\\`.
`roc macos.roc test --check` parses every spec without building or running
the app, on any system, and the spec's mistakes are reported where they are,
as its failures are.

The counter's `tests/specs/increment.scm` exercises the three increment
clicks and one decrement click, then checks the visible value and the view
tree.

[source,scheme]
----
include::../examples/counter/tests/specs/increment.scm[]
----

The platform performs each step on the app's real controls, through the same
action methods AppKit calls, without taking keyboard focus, opening a panel
or showing the crash alert, and prints what each expectation looks at; the
tool compares the results. A failure names the spec's file, line and
column.

[source,text]
----
FAIL tests/specs/increment.scm
  tests/specs/increment.scm:9:5: expected one (text "3"), saw none; the nearest are "2", "+", "−"
----

[#dumps]
=== Dumps

The window is an S-expression too. `(expect-dump TREE)` expects the whole
window, `(window :width W :height H …)` and every view in it, a node a line:
each node is its kind (`vstack`, `button`, `text`, `list` and so on), then
what it shows (a title, a text, a field's value), then keywords for what
differs from the usual (`:color secondary-label`, `:enabled #f`,
`:checked #t`, `:views 3`), then the nodes it holds. A list shows its
visible rows and `(more)` when there are others. `(expect-tree LOCATOR
TREE)` expects the one node a locator finds, such as
`(expect-tree (list-row "Ada A. Liskov") (row :views 2 (image _) _))`.

A spec's window is on the same virtual screen on every Mac, with room for
1440 × 840 points of content (a 1440 × 900 screen less its menu bar and
title bar), whatever display the run has; `(screen-size W H)` gives it
another. Content that needs more room than the window has scrolls, and the
window's node then says how big the content is:
`(window :width 600 :height 400 :content-height 912 …)`.

The comparison is node by node. `_` matches anything, a node or a word, so
a hand-written tree can say only what matters. A `:width` or `:height`
(and a `:content-width` or `:content-height`) may differ by up to 4
points, since sizes depend on the system's fonts.
Where a dump holds the app's directory (a file's URL, say), the directory is
written `<app>`, and the window's size, which depends on it, `_`. A
mismatch names the first node that differs by its path, its kind and place
among its parent's nodes from 1:

----
tests/specs/increment.scm:11:5: at window/vstack#1/vstack#1/hstack#3/button#2: expected "Rest", saw "Reset"
----

`roc macos.roc test --update` rewrites each `expect-dump` with what the app
shows now, a node a line from where the tree starts, and nothing else: an
`expect-tree`, like any other expectation, is never rewritten. Write
`(expect-dump _)` for it to fill in, and review the change before you commit
it.

[#locators]
=== Locators

A step finds what it acts on as a person would, by what it shows. An action
must find exactly one thing, and fails otherwise, naming the nearest texts
of that kind; an expectation reports how many it found.

[cols="1,3",options="header"]
|===
| Locator | Finds

| `(button "Save")` | the button with that title
| `(checkbox "Done")` | the checkbox with that title
| `(text "Ready")` | the innermost element showing exactly that text: a text, a button's title, a text field's value
| `(text-field)`, `(text-field "Search")` | every text field, or the one with that placeholder
| `(text-area)`, `(text-area "Notes")` | likewise for text areas
| `(list-row "Ada")`, `(list-row 3)` | the list row holding an element whose text is exactly that (built to be searched, if the list has not shown it yet), or the k-th row from 1 of the one list
| `(hover-target 3)` | the k-th element, from 1 in tree order, that listens for hover
| `(slider 6)` | the k-th slider, from 1 in tree order
| `(surface "Visualizer")` | the drawing surface with that label
| `(button "Remove" 2)` | the k-th, from 1 in tree order, of several buttons, checkboxes or texts with that title or text
| `(within OUTER INNER)` | INNER, looked for inside the one thing OUTER finds
|===

[#steps]
=== Steps

Steps run 100 ms apart.

[cols="1,3",options="header"]
|===
| Step | Does

| `(click LOC)` | clicks the button (a checkbox toggles); a disabled one fails the step
| `(fill LOC "text")` | sets a text field's or a text area's text, as typing it would
| `(submit LOC)` | submits the text field's form, as Return does
| `(toggle LOC)` | toggles the checkbox
| `(choose "title")` | chooses the item or segment of the one dropdown or segmented control that offers it
| `(select LOC)` | selects a list row, as a click does: `(list-row "text")` or `(list-row K)`
| `(slide LOC VALUE)` | moves a slider, `(slider K)`, to that value, as a drag ending there would
| `(scroll K)` | scrolls the first list so that its row `K` (from 0) is at the top
| `(press "cmd+shift+n")` | presses a key, delivered as if nothing had focus; the modifiers are `cmd`, `shift`, `ctrl` and `alt` (or `opt`). With `:heard true` (or `false`) it also expects the app to have handled the key, or not
| `(files "path" …)` | gives files as if picked on the one file button or drop zone, with no panel; paths are relative to the app's directory
| `(drop "path" …)` | gives files as if dropped on the one drop zone
| `(hover LOC)` | moves the pointer to the middle of the nearest `Ui.hover` at or around what LOC finds
| `(move X Y)` | moves the pointer to that point of the window's content, in points from its top-left corner
| `(leave)` | moves the pointer out of the window
| `(sweep X0 Y0 X1 Y1 MOVES MS)` | moves the pointer along a line in `MOVES` steps, one every `MS`; the next step follows the last move
| `(stats)`, `(phase "name")` | with `ROC_BENCH=1`, print the timings so far, and report the operations from here on apart, as `event/<name>` and so on
| `(window)` | prints `window <number>` on standard error, for `screencapture -l<number>`
| `(wait MS)` | waits
| `(reload)` | reloads as Command-R does (xref:apps.adoc#hot-reloading[Hot reloading]): a fresh engine and view tree in the same window; the steps after it drive the fresh one
|===

The pointer steps drive the same hit test the mouse does, and a driven run
ignores the real mouse, so where your pointer happens to be never changes a
run. A spec ends after its last step, through the same teardown as quitting.

[#expectations]
=== Expectations

[cols="1,3",options="header"]
|===
| Expectation | Holds when

| `(expect-text LOC "text")` | the one thing LOC finds shows exactly that text: a button's or checkbox's title, a field's value, a dropdown's chosen item, a progress bar's `3/8`, or a text
| `(expect-visible LOC)` | LOC finds exactly one thing
| `(expect-absent LOC)` | LOC finds nothing
| `(expect-checked LOC true)` | the checkbox is checked (`false`: unchecked)
| `(expect-disabled LOC true)` | the control is disabled (`false`: enabled)
| `(expect-workers …)` | the worker pool's counts it names, such as `:answered 8`, are these
| `(expect-dump (window …))` | the window and its view tree are this tree (xref:apps.adoc#dumps[Dumps])
| `(expect-tree LOC (kind …))` | the one node LOC finds is this tree
|===

`expect-workers` names any of the pool's counts: `:limit`, `:live`,
`:running`, `:queued`, `:started`, `:answered`, `:lost`, `:stopped`,
`:timed-out` and `:dropped`.

[#effects-in-a-spec]
=== Effects

By default, a spec holds HTTP requests, timers and intervals for the spec
to answer. It numbers them from 1 in issue order. The virtual clock starts
at `(initial-time MS)`, which defaults to the Unix epoch. Advance it with
`(advance-time MS)` to exercise a stopwatch or a timeout.

Worker jobs and file reads run for real. Use `(await-work)` to wait for
them. In setup, `(worker-pool 1)` runs jobs one at a time, in issue order.
Storage reads answer on their own. Reload restarts effect numbering and
keeps the clock's current time.

[cols="1,3",options="header"]
|===
| Step | Does

| `(stub-http "label" :status 200 :body "…")` | stages the answer the next `run-effect` of an HTTP request gives: a status from 100 to 999 (200 by default), a body, `:headers (("name" "value") …)`, and with `:url "…"` the URL the request must have. One answer is staged at a time
| `(fail-http "label" :kind network :detail "…")`, `(fail-http "label" :kind timeout)` | stages a failure instead: the network's message, or a timeout
| `(run-effect N)` | answers effect `N`, which must be pending: an HTTP request with the staged answer, a timer by firing it at the clock's time
| `(tick-interval MS)` | ticks every live interval of that period, at the clock's time; fails when there is none
| `(fire-timer MS)` | fires the first pending timer of that delay
| `(advance-time MS)` | moves the clock on; an HTTP request whose timeout has passed answers `Timeout`, in issue order
| `(await-work)` | waits for every worker job and file operation in flight, at most 30 seconds
|===

[cols="1,3",options="header"]
|===
| Expectation | Holds when

| `(expect-pending-effects N)` | `N` HTTP requests, timers, worker jobs and file operations are waiting to be answered (intervals are not counted: see `expect-interval`)
| `(expect-interval MS N)` | `N` intervals of that period are live
| `(expect-request N :method "GET" :url "…")` | effect `N` is an HTTP request with those fields, any of `:method`, `:url`, `:body` and `:timeout` (in milliseconds, 0 for none)
| `(expect-cancelled N)` | the app cancelled effect `N`
|===

[source,scheme]
----
(test "a refused connection says why"
  (steps
    (fill (text-field) "http://127.0.0.1:9/")
    (click (button "Fetch"))
    (expect-request 1 :method "GET" :url "http://127.0.0.1:9/")
    (fail-http "refused" :kind network :detail "Could not connect to the server.")
    (run-effect 1)
    (expect-text (text "#1: Could not connect to the server.") "#1: Could not connect to the server.")
    (expect-pending-effects 0)))
----

[#work-metrics]
=== Work metrics

The engine counts the work each turn does, and returns the counts with it.
`(mark-metrics)` notes them, and each later
`(expect-metric-delta METRIC N)` expects a metric to have changed by
exactly `N` since, `(expect-metric-delta-at-most METRIC N)` by at most
`N`. Expect structural work exactly, since it is what the window shows, and
bound incidental work, such as how many of the app's functions ran, with
`-at-most`, so that a faster engine does not fail the spec. With no mark
before it, a change is measured from the window's mount. A reload starts the
counts again, so mark after it.

[source,scheme]
----
(test "a click writes one text"
  (steps
    (mark-metrics)
    (click (button "+"))
    (expect-metric-delta set_text 1)
    (expect-metric-delta create_element 0)
    (expect-metric-delta-at-most derived_calls_into_roc 2)))
----

The metrics are roc-signals': `rows_created`, `rows_removed`, `rows_reused`,
`rows_updated`, `rows_moved`, `create_element`, `set_text`, `set_value`,
`set_checked`, `bind_event`, `registrations_released`, `set_metadata`,
`patches_emitted`, `derived_calls_into_roc`, `scopes_created`,
`scopes_disposed`, `dirty_source_roots`, `each_key_hashes`,
`each_key_compares`, `turns`, the effect counts `effects_issued`,
`effects_delivered`, `effects_stale`, `effects_refused`,
`effects_cancelled`, `effects_reparented`, `effects_skipped` and
`effects_progress`, `view_transitions`, `startup`, `startup_ack`,
`startup_complete`, and `opportunity_commands`, `opportunity_requested`,
`opportunity_cancelled`, `opportunity_delivered` and `opportunity_stale`.
roc-signals' testing guide describes what each counts.

[#allocations]
=== Allocations

A Roc app's memory is reference counted, and a value nobody else holds is
updated in place: appending to a list, writing a record's field or a
table's row reuses the memory it had. A change that makes a value shared,
such as keeping an old copy around or passing it where it is held, turns
that in-place update into a copy, which shows up as allocations and nothing
else: the app still looks the same and is only slower. So the allocations
a step makes are worth guarding, the way a test guards what it shows.

While a spec runs, the platform counts the page instance's calls of
`roc_alloc`, `roc_realloc` and `roc_dealloc`, and the bytes the
allocations and reallocations asked for. A worker job's heap is not
counted. They are metrics like the engine's, measured from a
`(mark-metrics)` (or, with none, from the window's mount):

[cols="1,3",options="header"]
|===
| Metric | Counts

| `allocations` | `roc_alloc` calls
| `reallocations` | `roc_realloc` calls (a list growing past its capacity)
| `deallocations` | `roc_dealloc` calls
| `live_allocations` | allocations less deallocations: what is still held
| `allocated_bytes` | the bytes allocations and reallocations asked for
|===

[cols="1,3",options="header"]
|===
| Expectation | Holds when

| `(expect-allocations-at-most N)` | at most `N` allocations since the mark
| `(expect-allocated-bytes-at-most N)` | at most `N` bytes asked for since the mark
| `(expect-no-new-live-allocations)` | no more is held than at the mark: the steps since leave nothing behind
| `(expect-metric-delta-at-most allocations N)` | the same as the first, and so for every metric above
|===

[source,scheme]
----
(test "work"
  (steps
    (mark-metrics)
    (click (button "+"))
    (expect-allocations-at-most 12)
    (expect-allocated-bytes-at-most 900)
    (expect-no-new-live-allocations)))
----

The workflow is a ratchet:

. *Measure.* `roc macos.roc test --metrics` runs every spec and prints, for
  each step that expects a metric, every allocation metric and each work
  metric that changed, since its mark; and for the whole run since mount.
  It judges nothing.
. *Set a bound.* Write `(expect-allocations-at-most N)` with what it
  measured, after the steps you care about, such as a click or a tick.
. *Ratchet down.* When a change makes the app allocate less, `roc
  macos.roc test --update` lowers each allocation bound (of `allocations`,
  `reallocations` or `allocated_bytes`) to what the run measured, along
  with the dumps; review the diff and commit it. It never raises a bound: a
  run that allocates more fails, saying how many it saw against the bound,
  and either the app or the bound is then wrong on purpose.

The counts depend on the Roc compiler as much as on the app: another
version can make more or fewer allocations for the same code. A spec's
bounds hold for the toolchain the app is tested with (this release names
it); when you move to another compiler, measure again and set them anew.

[#surfaces-and-audio]
=== Drawing surfaces and audio

In a spec, display-paced surfaces draw only on `frame` steps, on a clock
that starts at 0 and moves only when a step moves it, and the synthetic
sources move only on `step-source`; the same steps draw the same frames on
any Mac. A spec draws with Core Graphics unless `(renderer metal)` says
otherwise, and a Mac with no Metal device draws with Core Graphics then too,
so the pixels a spec probes are the same either way. A surface's shaders
(xref:ui.adoc#shaders[Shaders]) are the exception: they run only with
Metal, so a spec that probes them starts `(require-metal) (renderer metal)`,
and another with `(renderer cg)` checks what the surface draws without them;
a spec compiles them before its next step, and its dump shows each shaded
surface's `:shader running`, `failed` or `fallback`. `expect-probe` draws at
2 pixels a point, whatever the screen, so probe away from the edges of
shapes. A dump shows each surface with its size, pacing and trail, and the
last frame's scene: the space it maps from and each figure's points in scene
units, each transform, save and restore, as `(surface "Visualizer" :width
428 :height 160 :pacing display :ticking #t (space :fit 640.0 160.0 :scale
0.669 :offset 0.0 26.5) (stroke green 3.0 0.0,20.0 …))`.

With `(audio-clock manual)` in the setup, the playback session (`Audio`)
renders offline at 48 kHz, never to a speaker, and only `render` moves it,
so its reports are the same on every run. Its fixtures, such as the player
example's `tests/fixtures/*.wav`, are generated by
`scripts/audio_fixtures.roc`.

[cols="1,3",options="header"]
|===
| Step | Does

| `(frame)`, `(frame MS)` | moves the frame clock on by `MS` milliseconds (a 60 Hz refresh, 16.667, if none), and draws one frame on every display-paced surface
| `(frame-clock display)`, `(frame-clock manual)` | draws display-paced surfaces at the display's refresh from here on, with the synthetic sources moving with time (for a demo), or back to `frame` steps
| `(step-source "synthetic.wave")`, `(step-source "synthetic.level" N)` | moves a synthetic source on by one step (or `N`), an eighth of a cycle
| `(repaint)` | redraws every surface now, as AppKit may at any time, without a new frame
| `(window-size W H)` | sets the window's content size, in points, within the room its screen has (the window then fits its content again on the next turn, as it always does)
| `(screen-size W H)` | puts the window on a screen with room for `W` by `H` points of content, in place of the spec's usual 1440 by 840 (xref:apps.adoc#dumps[Dumps]), and fits it again
| `(renderer metal)`, `(renderer cg)`, `(renderer auto)` | draws display-paced surfaces with Metal (Core Graphics on a Mac without a device), with Core Graphics (a spec's default), or with Metal where there is a device, from here on
| `(require-metal)` | ends the spec here, passing, on a Mac without a Metal device (or with `ROC_SURFACE_RENDERER=cg`), so the steps after it, which need shaders to run, are judged only where they can
| `(bench-surfaces N)` | draws `N` trail frames offscreen at three sizes with each renderer, then each surface running shaders `N` times at 1600 × 1000, 2560 × 1664 and 2880 × 1800 pixels, and prints the time a frame (the shaders' GPU time alone) on standard error; it measures this Mac, so it is reported and never judged
| `(render MS)` | with `(audio-clock manual)`, renders `MS` of output, pausing whenever the measurements fall behind so that every chunk is measured (none dropped, so the same steps measure the same windows on every run), then publishes the status and the newest measurement
| `(stall-analysis true)`, `(stall-analysis false)` | stops and restarts the analysis worker taking chunks, as a worker that falls behind would
| `(require-av-timing)` | ends the spec here, passing, unless `ROC_AV_TIMING=1`: the steps after it play to the real output and draw at the display's pace (xref:apps.adoc#av-sync[Measure audio/visual sync])
| `(mark-av-timing)` | starts the audio/visual timing report again from now
|===

[cols="1,3",options="header"]
|===
| Expectation | Holds when

| `(expect-probe (surface "label") X Y :r 100 :g 0 :b 0 :a 50)` | the surface shows that colour at that point, in points from its top-left corner, as whole percentages of red, green, blue and opacity; any of the four, each exactly or within `:tolerance N` percentage points (below)
| `(expect-surfaces :shown 1 :ticking 1 :time "200.0")` | that many surfaces are shown and on the frame clock, and the clock is at that time in milliseconds; any of the three
| `(expect-audio-status :state "Playing" :position 200 :duration 500 …)` | the transport: `:state` (`Idle`, `Stopped`, `Playing`, `Paused`, `Ended`), `:position` and `:duration` in ms, `:track`, how many times it has `:ended`, and whether the `:analysis` runs
| `(expect-tone HZ DBFS)`, `(expect-tone HZ silent)` | the `HZ` component of the last render's output is at that level, in whole dBFS (a full-scale sine is 0)
| `(expect-eq :bypass false :preamp 0 :bands "0 0 0 -12 0 0 0 0 0 0" :volume 100)` | the EQ as it applies: bypass, the preamp and each band's gain in whole dB, and the volume in percent
| `(expect-snapshot :present true :at "267.0" :rate 44100 :rms -20 :peak -14 :finite true :loudest "7 -20, 18 -20")` | the newest measurement: its time in ms, sample rate, RMS and peak level in dB, whether every value is finite, and its two loudest bands above -60 dB with their levels (`"none"` if no band is); `:present false` when there is none yet
| `(expect-history :count 5 :bound 32 :first "46.4" :last "139.3" :current true :ordered true :waiting 0 :slots 4 :skipped false)` | the measurements kept: how many of the bound, the first's and last's times (`"-"` when empty), whether all are of the current source position and in order, and the analysis ring's chunks waiting of its slots, and whether older ones were skipped
| `(expect-sources :waveform "1024 -0.20 0.20" :level "0.67" …)` | what a drawing surface would read now from each `audio.*` source: a series' count, least and greatest value, a number, or `"none"` (the sources are below)
| `(expect-av-offset :mean-within 30 :p95-within 45 :lead-at-most 15 :matched-at-least 10)` | since the mark, each click heard matched to the flash the busiest display-paced surface showed for it, in milliseconds (positive: the picture trails): the mean offset's size, the 95th percentile and the largest of the offsets' sizes (`:max-within`), how far the earliest flash led its click, and how many clicks had a flash; bounds, not values
| `(expect-frame-pacing :dropped-at-most 3 :p99-at-most 25)` | that surface's refreshes missed between display-link ticks, frames the GPU was too far behind to draw (`:skipped-at-most`), the 99th percentile of the time between frames presented, in milliseconds, the 99th percentile of the GPU's time a frame (`:gpu-p99-at-most`), and how many frames were drawn (`:frames-at-least`)
|===

`expect-sources` names any of the sources `:waveform`, `:left`, `:right`,
`:bands`, `:level`, `:bass`, `:mids` and `:treble`.

A spec draws every surface at twice its size in points, whatever the
display's backing scale, so a probe reads the same pixels on a 1× screen
as on a Retina one. Probe well inside a shape, not on its edge, where
smoothing decides the colour. Core Graphics draws the same pixels on every
Mac, so its probes match exactly; Metal's shaders may round a unit or two
differently on another GPU, so a shader's probe names a `:tolerance`, such
as `:tolerance 3`. The named colours (`orange`, `red`, …) are the
system's, which macOS releases change (macOS 26's orange is not macOS
15's): probe the channels a test means, such as `:r 100 :a 100` for an
orange pen, or draw with an explicit colour.

[#av-sync]
==== Measure audio/visual sync

A visualization should move with what the listener hears. The platform
measures it end to end: play a click track (the visualizer's
`tests/fixtures/sync-clicks.wav`, a 5 ms burst every 500 ms, made by
`scripts/audio_fixtures.roc`) through a preset that flashes with the level
(the visualizer's Sync Test, or the starter's), and the host times each click
as it is heard and each flash as it reaches the screen:

* *Heard*: the render time stamp of the buffer that holds the click's first
  sample (its host time, from the measuring tap's render notification), plus
  the click's place in that buffer at the source's rate, plus the output's
  latency (`latency_ms`: the larger of AVAudioEngine's
  `outputNode.presentationLatency` and Core Audio's device and stream
  latency).
* *Seen*: the presented time (`CAMetalDrawable.addPresentedHandler`) of the
  first frame presented at or after the first frame whose `audio.level`
  reaches 0.5. Core Graphics has no presented time, so its frames count as
  seen at their display-link target.

The offset is seen less heard. A spec measures it on the real clock, so it
runs only with `ROC_AV_TIMING=1`, and passes at `(require-av-timing)`
otherwise:

[source,scheme]
----
(test "av-sync"
  (steps
    (require-av-timing)
    (require-metal)
    (renderer metal)
    (frame-clock display)
    (choose "Gallery")
    (choose "Sync Test")
    (files "tests/fixtures/sync-clicks.wav")
    (wait 500)
    (mark-av-timing)
    (wait 6000)
    (expect-av-offset :mean-within 30 :p95-within 45 :lead-at-most 15 :matched-at-least 10)
    (expect-frame-pacing :dropped-at-most 6 :p99-at-most 25)))
----

An app run with `ROC_AV_TIMING=1` (no spec) prints the same report on
standard error every five seconds: the clicks and flashes matched, the
offsets' mean, 95th percentile and extremes, every offset, the output
(its name and each part of its latency), how far behind its window's
centre each frame was seen, how far behind its display-link target each
frame was presented, and the frame pacing and GPU time. `ROC_AUDIO_DEVICE`
plays to another output, to measure it there. A measurement says what the
system reports; only a camera and a speaker can say what a person sees and
hears, so a release is also checked by eye
(xref:contributing.adoc#av-sync-by-hand[Audio/visual sync by hand]).

[#the-spec-protocol]
=== Under the hood

`ROC_SPEC` holds the steps the tool lowered from a spec, one line each; the
platform performs them and prints one tagged observation per expectation on
standard output (`@3 obs`, then `|count 1`, `|text 2`, or a dump's tree a
node a line), which the tool compares. The app's own output, such as `dbg`, goes to standard error, which
a failure shows the end of.

[#environment-variables]
=== Environment variables

The platform reads these when the app starts. Set them on the command line,
as in `ROC_APPEARANCE=dark roc macos.roc dev`.

[cols="1,3",options="header"]
|===
| Variable | Effect

| `ROC_SPEC` | performs these lowered spec steps, as `roc macos.roc test` does (xref:apps.adoc#the-spec-protocol[Under the hood])
| `ROC_APPEARANCE=dark` (or `light`) | draws the app in that appearance whatever the system's, to check both looks
| `ROC_TRACE=1` | logs effect requests, cancellations, minted and released file handles, worker jobs (queued, placed, answered, stopped, timed out, dropped) and worker threads (started, unwound, ended), the teardown (`DROP`), and each turn's engine and host time
| `ROC_BENCH=1` | times each operation (a mount, an event, a pointer move, a timer, a spec's scroll) in four phases: engine, applying the commands, layout and a forced display, and shows them live in a panel over the window; `stats` prints them with the view count and RSS
| `ROC_POISON=1` | fills every new allocation with `Z`, to expose reads of uninitialised memory
| `ROC_SAVE_DIR` | where a driven run's save writes; without it a driven run's save is skipped
| `ROC_MAX_FILE_BYTES` | lowers the file ceiling, to check `TooLarge`
| `ROC_WORKERS=<n>` | the worker pool's size (one per core but one, at most eight, otherwise)
| `ROC_MAX_OUTPUT_BYTES` | lowers what one worker job may append to its builders (256 MiB), to check `TooLarge`
| `ROC_STORAGE_SUITE=<name>` | a `UserDefaults` suite for local storage; otherwise a driven run's local storage is in memory
| `ROC_SURFACE_RENDERER=<auto, metal or cg>` | which renderer draws display-paced surfaces: Metal where there is a GPU (`auto`, the default outside a spec), Metal falling back to Core Graphics (`metal`), or Core Graphics (`cg`, a spec's default)
| `ROC_SURFACE_TIMING=1` | prints each Metal surface's GPU time a frame (mean and most) on standard error every two seconds, to measure a shader
| `ROC_SURFACE_SHOTS=<dir>` | writes each Metal surface's frame as `<dir>/<label>-<n>.png` every two seconds of frame time, to look at a shader's picture
| `ROC_AV_TIMING=1` | records the audio/visual timing harness from launch and prints its report on standard error every five seconds; in a spec, runs the steps after `(require-av-timing)` (xref:apps.adoc#av-sync[Measure audio/visual sync])
| `ROC_AUDIO_DEVICE=<name or UID>` | plays the playback session to that output device instead of the system's default output; a name that matches none is a fatal error listing the outputs
| `ROC_ASSETS=<dir>` | the app's assets directory, for a program run away from its `assets/` (see xref:apps.adoc#assets[Assets and the icon])
|===

[#fuzz-the-logic]
=== Fuzz the logic

https://github.com/lukewilliamboswell/roc-fuzz[roc-fuzz] checks a property
of pure Roc code against inputs it generates and mutates, with coverage
feedback. `tests/fuzz/main.roc` is an app on roc-fuzz's platform that imports the
logic package as `src/main.roc` does, and declares its targets:

[source,roc]
----
target = Fuzz.suite([lrc_parse, lrc_round_trip, json_round_trip, preset_decode, preset_round_trip, queue_invariants])

json_round_trip = Fuzz.target_with({
	name: "json-round-trip",
	generator: Fuzz.str,
	test: |text|
		match JsonValue.parse(text) {
			Ok(value) => if (JsonValue.parse(JsonValue.encode(value)) == Ok(value)) Fuzz.keep else crash "${Str.inspect(text)} did not encode and parse back"
			Err(_) => Fuzz.keep
		},
	show: Str.inspect,
	examples: [Fuzz.example({ name: "deep", revision: "1", make: || Str.repeat("[", 40) })],
})
----

`roc macos.roc fuzz` builds it with `roc build --fuzz tests/fuzz/main.roc` into
`.macos/fuzz` and runs each target in turn for 10 seconds, keeping the
inputs worth revisiting in `.roc-fuzz/corpus/<target>`;
`roc macos.roc fuzz lrc-parse --time 300` runs one target for longer, and
`roc macos.roc fuzz --check` runs only the examples each target declares,
quickly, as the release workflow does. A failure prints its report and
leaves the failing input under `.roc-fuzz/`, which
`.macos/fuzz --target=NAME replay INPUT` runs again; roc-fuzz's
https://lukewilliamboswell.github.io/roc-fuzz/[manual] covers minimizing it
and keeping it as an example. roc-fuzz runs on Apple silicon Macs and Linux
x64. Saved and mutated inputs bypass a generator's bounds, so a property
states its preconditions again and returns `Fuzz.reject` outside them.

[#ship-your-app]
== Ship your app

`roc macos.roc package` builds the app and writes
`dist/<name>-<version>.zip`, the file people download. It works on macOS,
Linux and Windows. How freely the app then opens on another Mac depends on
who signed it, in three tiers: share it with friends, distribute it with a
Developer ID, and let GitHub do either when you push a tag.

The zip holds `<name>.app` with each entry's Unix mode set by the tool
(directories and the program 0755, other files 0644), so the program keeps
its execute bit whichever system made the zip: a zip made on Windows, or by
many tools, loses it, and macOS then will not launch the app. With
identical bundle bytes and timestamps, packaging produces identical ZIP
bytes. Entries are sorted and stamped with 1980-01-01 by default. Set
`SOURCE_DATE_EPOCH` to use a different timestamp. Signing and notarization
can change the bundle bytes. The ZIP uses DEFLATE compression through
https://github.com/lukewilliamboswell/roc-zip[roc-zip].

[#share-with-friends]
=== Share it with friends

With no Apple account, `package` seals the app ad hoc:

[source,sh]
----
roc macos.roc package --version 1.0.0
----

Roc's linker signs only the program, so `package` signs the whole bundle,
which covers its `Info.plist` and resources too: with `codesign` on a Mac,
or with https://github.com/indygreg/apple-platform-rs/releases[`rcodesign`]
(apple-codesign, on any system) when it is on your PATH. Without either, it
zips the app unsealed and says so.

Gatekeeper can block the first launch of a downloaded app with an ad hoc
signature. If the recipient trusts the source and has verified the download,
they can try opening it and then choose Open Anyway in System Settings >
Privacy & Security. See https://support.apple.com/en-us/102445[Apple's
instructions for opening apps safely].

[#distribute]
=== Distribute it with a Developer ID

For wider distribution outside the Mac App Store, sign the app with a
Developer ID and notarize it with Apple. This requires membership in the
https://developer.apple.com/programs/[Apple Developer Program] and two
credentials:

* A *Developer ID Application certificate*. The account holder creates it in
  Xcode (Settings > Accounts > Manage Certificates > + > Developer ID
  Application), or at developer.apple.com under Certificates, IDs &
  Profiles. Keychain Access then exports it, with its private key, as a
  `.p12` file protected by a password.
* An *App Store Connect API key*, for notarization: in App Store Connect,
  Users and Access > Integrations > App Store Connect API, generate a team
  key with the Developer role. Note its Issuer ID and Key ID, and download
  its `AuthKey_<id>.p8` file. Save it securely because Apple offers the
  download once.
  https://developer.apple.com/documentation/appstoreconnectapi/creating-api-keys-for-app-store-connect-api[Create API keys]

`package --sign` signs the app with the certificate, with the hardened
runtime and a secure timestamp. `package --notarize` also signs it, sends
the zip to Apple's notary service, waits for its answer (usually a few
minutes), staples the ticket to the app and zips it again. The tool reads
the credentials from the environment, never from its command line, and
writes any it must pass to a signing tool to `.macos/secrets/`, readable by
you alone, which it removes when it finishes:

[cols="1,3",options="header"]
|===
| Variable | What it is

| `MACOS_SIGN_IDENTITY` | on a Mac, the certificate's name in your keychain, such as `Developer ID Application: Jane Doe (TEAMID)`; `codesign` signs with it and `notarytool` notarizes
| `MACOS_SIGN_P12` | anywhere, the path of the certificate's `.p12` file; `rcodesign` signs and notarizes with it
| `MACOS_SIGN_P12_PASSWORD` | the `.p12` file's password
| `MACOS_NOTARY_ISSUER` | the API key's Issuer ID
| `MACOS_NOTARY_KEY_ID` | the API key's Key ID
| `MACOS_NOTARY_KEY` | the `.p8` file's path, or its contents
| `MACOS_SIGN_TOOL` | `codesign` or `rcodesign`, to choose the tool when both are here
|===

On a Mac, with the certificate in your keychain:

[source,sh]
----
export MACOS_SIGN_IDENTITY="Developer ID Application: Jane Doe (TEAMID)"
export MACOS_NOTARY_ISSUER=… MACOS_NOTARY_KEY_ID=… MACOS_NOTARY_KEY=~/keys/AuthKey_ABC123.p8
roc macos.roc package --version 1.0.0 --notarize
----

On Linux or Windows, the same with `MACOS_SIGN_P12` and
`MACOS_SIGN_P12_PASSWORD` in place of `MACOS_SIGN_IDENTITY`, and `rcodesign`
on your PATH. The app needs no entitlements under the hardened runtime: Roc
compiles it ahead of time, so it makes no executable memory, and it is not
sandboxed, so it needs none to reach the network or the files a person picks.

[#automate]
=== Let GitHub release it

`init` writes `.github/workflows/release.yml`. Push a tag and it releases
the app:

[source,sh]
----
git tag v1.0.0
git push origin v1.0.0
----

Each of its steps is one command: the workflow runs the app's `expect`
tests and specs on a macOS runner (`roc macos.roc test`) and, when
it has `tests/fuzz/main.roc`, its fuzz targets' examples
(`roc macos.roc fuzz --check`), then packages the app on
Linux (`roc macos.roc ci package`), and attaches `<name>-1.0.0.zip` to the
tag's GitHub release, creating the release if there is none
(`roc macos.roc ci release`). A tag with a suffix, such as `v1.0.0-beta.1`,
makes `<name>-1.0.0-beta.1.zip` and a GitHub pre-release; the app's
`Info.plist` says 1.0.0.

`ci package` is `package` deciding for itself, so that the workflow needs no
script: the version is the tag without its `v` (or the version "Run
workflow" was given, as `RELEASE_VERSION`); it signs or notarizes according
to which secrets are set, and says in the run's summary which are missing;
it decodes the certificate to a file only the job can read, removed
afterwards; it installs a pinned `rcodesign`, checked against its SHA-256,
when it signs with a certificate; and the zip's entries carry the last
commit's time. `roc macos.roc ci --help` describes it. With no secrets it
seals the app ad hoc. To sign
and notarize it, add these secrets to the repository (Settings > Secrets
and variables > Actions), or to its `release` environment (Settings >
Environments), which the packaging job runs in and which you can limit to
tags or to a reviewer's approval:

[cols="1,3",options="header"]
|===
| Secret | What it is

| `MACOS_SIGN_P12_BASE64` | the certificate's `.p12` file, base64-encoded, as `base64 -i developer-id.p12` prints it
| `MACOS_SIGN_P12_PASSWORD` | its password
| `MACOS_NOTARY_ISSUER` | the API key's Issuer ID
| `MACOS_NOTARY_KEY_ID` | the API key's Key ID
| `MACOS_NOTARY_KEY` | the `.p8` file's contents
|===

With only the first two, the app is signed but not notarized; some of the
notary secrets without the rest is refused. The workflow installs the Roc
nightly the platform release was tested with; every action is pinned by its
full commit SHA, the
jobs that see the secrets have a read-only token, and the one job that
writes the release sees no secret. "Run workflow" on the Actions tab
packages a version you give as a workflow artifact, and publishes nothing.
If the app is not at the repository's root, move the workflow to the root's
`.github/workflows/` and set its `APP_DIR` to the app's directory. Specs
need a macOS runner, which costs more minutes in a private repository;
to skip them, delete the `test` job and the package job's `needs: test`.
For an app made before the tool wrote the workflow, run `roc macos.roc init`
in an empty directory and copy the file from there.

[#without-the-tool]
=== Without the tool

`roc macos.roc build` works the same on macOS, Linux and Windows: the
platform carries everything the link needs, and Roc's linker signs the
program ad hoc wherever it is built. Without the tool, name the Mac to
build for yourself, since the platform's targets are macOS ones (`roc`
builds for the machine it runs on by default):

[source,sh]
----
roc build src/main.roc --target=arm64mac   # Apple silicon
roc build src/main.roc --target=x64mac     # Intel
----

`roc build` makes one program for one Mac, as `roc macos.roc build --target`
does; `roc macos.roc build` makes both and joins them into a universal one. On an Intel Mac, `roc src/main.roc` and a
bare `roc build` need no `--target`. A machine whose CPU does not report
x86-64-v3 (an Intel virtual machine, say, or Rosetta) gets Roc's baseline
target, `x64v1mac`, which the platform supports too.

`--opt=speed`, `--opt=size` and `--opt=dev` can cross-compile, with either
`--specialize=yes` or `--specialize=no`. `--opt=interpreter` builds only for
Roc's native target. Use `x64v1mac` for Intel builds to run under Rosetta, the
target the xref:contributing.adoc#intel-macs[platform's build matrix]
exercises there.

When Gatekeeper blocks a downloaded ad hoc build, follow the steps in
xref:apps.adoc#share-with-friends[Share it with friends].
